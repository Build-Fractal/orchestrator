### Dangerous Contradictions

- **[index-free guarantee over an empty store]** — pipeline-reliability's headline recommendation is to make the index-free deterministic-grep fallback a mandated, enumerated, fixture-byte-equality-tested invariant for *every* index consumer (`pipeline-reliability/review.md` L15, Rec 1 L67, Rec 11 L87: "the index-free guarantee is the one P1 item that is itself a proven-bug surface"). My review holds that B-3 (BUG A, format mismatch) is a *source-of-truth* failure that a correct index/grep cannot recover from (`activation-loop/review.md` L29: "A correct index over BUG-A rows still mis-extracts scope/when"). **Why dangerous (false-safety failure mode):** a perfectly resilient, byte-equality-locked, index-free grep fallback running over a store whose *rows are mis-columned* (B-3) or *never written* (G-1) still injects nothing useful — grep-over-raw-files finds the row, but `filter_decisions` extracts scope from the wrong field and the scope-match drops it, OR there is no row to find at all. Hardening the retrieval pipeline while the capture format is broken ships a trust receipt that certifies an empty/unparseable corpus as "activated." That is exactly the fail-open P-A forbids, re-dressed as a green deterministic log. **Suggested cooperative resolution:** sequence the round-trip parser-unification (FR-1, B-3) as a *prerequisite* of the index-free fixture suite — the byte-equality fixtures pipeline-reliability wants (their Rec 3) must assert over rows produced by the *unified* producer, so the same fixture corpus locks BOTH the capture format and the grep fallback. One corpus, two guarantees; neither ships green alone.

- **[fixture-byte-equality for grep vs round-trip non-determinism]** — pipeline-reliability wants every regression locked at fixture-byte-equality including the grep fallback output (Rec 3 L71, Rec 6 L77). My review endorses the grep-floor for the round-trip's *immediate confirmation* step (`activation-loop/review.md` Rec 10 L120-125: the capture command's "confirms the entry resolves" must be deterministic, same-instant). **Why dangerous:** these *agree* on grep-as-floor, but a byte-equality fixture over grep output and a "just-captured entry resolves immediately" assertion can collide if the fixture pins a *static* expected corpus while the round-trip test writes a *fresh* entry at runtime — the fixture's frozen expected-output cannot contain the dynamically-appended row. Run naively, one test's expectation invalidates the other. **Suggested cooperative resolution:** split the harness: (a) static byte-equality fixtures for the rebuild summary / provenance header / archive-glob (pipeline-reliability's domain, no live writes); (b) a *round-trip* oracle that writes → rebuilds → greps → asserts the written entry is present (my AC-1 domain, dynamic). Same determinism discipline (`LC_ALL=C`, no wall-clock), different assertion shape. Don't force the round-trip into a frozen-corpus fixture.

- **[P0 scope: pipeline bugs vs the missing-capture half]** — pipeline-reliability keeps the §7 P0/P1 split largely as-is, pulling only the index-free regression into P0 (Rec 11 L87), and otherwise treats the capture-loop (G-1/G-4/FR-7/FR-8) as correctly P1. My review argues G-1 (Quick captures nothing) and FR-8's explicit-decision-capture belong in P0 because the field note's 0-MEM-for-two-milestones outcome was caused as much by *no default capture path* as by the rebuild bug (`activation-loop/review.md` L9, L31, L33). **Why dangerous:** if P0 ships pipeline-reliability's full hardening (resilient rebuild + index-free fallback + provenance + freshness) but defers all capture, the acceptance battery goes green on a hand-seeded fixture corpus while a *real default (Quick) project still produces 0-MEM injects* — the precise field-note failure, now with a clean bill of health from the hardened pipeline. The hardening makes the emptiness *loud* (FR-15 0-MEM warning), which is genuine progress, but "loudly empty" is not "activated." **Suggested cooperative resolution:** both perspectives already converge on FR-15 (the 0-MEM warning) as the P0 bridge. Accept FR-15 + the index-free fallback as the P0 "make-it-loud" floor (pipeline-reliability's win), AND pull the explicit-decision-capture half of FR-8 + Quick-includes-Decisions FR-6 into P0 (my win) so the loud signal has a populated store to point at. The auto-graduate-from-execution-log half stays P1 (needs a qualification rule).

### Tensions

- **[which silent failure is more damaging: cache-rebuild vs source-of-truth]** — *Their position:* the rebuild/index pipeline failing closed-silent (B-1) is the load-bearing, month-long, trust-eroding bug; the index is the spine and its resilience is P0-primary (`pipeline-reliability/review.md` L11, L13). *My position:* B-3 (the canonical store itself is unreadable) is strictly more fundamental — P-B explicitly *permits* the cache to be absent, so a cache failure is recoverable by definition, whereas a source-of-truth format failure corrupts every downstream path including the grep fallback (`activation-loop/review.md` L29). *Nature of tension:* productive ordering disagreement, not contradiction — we both want both fixed in P0; we differ on which is "co-primary." Their P0 = pipeline-integrity; my P0 = format-mismatch + capture-by-default. *Coordination needed:* agree the P0 list is *unordered* (both B-1 and B-3 are co-primary) and that §8/§7 narrative stops leading exclusively with the rebuild story. pipeline-reliability's own framing ("the index is a cache, the corpus is truth") logically *concedes* my point — a truth-layer bug outranks a cache-layer bug under their own principle.

- **[enumerate-every-consumer vs the consumer that doesn't read at all]** — *Their position:* enumerate every reader of `KNOWLEDGE-INDEX.md`/`knowledge.db`/`resolve-entries.sh` and give each an index-free path + provenance (Rec 1, Missed-Opp L39). *My position:* the most consequential "consumer gap" is not an unenumerated index reader — it's that the injector *never reads runtime agent memory at all* (G-3 two-store divergence), so no amount of consumer enumeration over the index/db reaches the store where decisions actually landed (`activation-loop/review.md` L23, L35). *Nature of tension:* complementary blind-spots — their enumeration is horizontal (all readers of the known stores), mine is vertical (a whole store the readers can't see). *Coordination needed:* the consumer inventory pipeline-reliability wants (Rec 1) should explicitly include the *negative* finding — "runtime agent memory is a store with zero readers" — so the enumeration surfaces G-3 rather than enumerating only the stores that are already wired.

- **[byte-stable provenance header schema vs round-trip confirmation reuse]** — *Their position:* pin the provenance header to a versioned byte-stable contract with fixed key order + `schema_version` so M034/M038/wiki consumers parse it deterministically (Rec 4 L73, Missed-Opp L41). *My position:* the same provenance/confirmation surface must also serve the capture command's "confirms the entry resolves in an inject" step (`activation-loop/review.md` Rec 5 L87: confirmation reuses the AC-1 oracle). *Nature of tension:* shared artifact, two consumers — their consumer is downstream parsers, mine is the synchronous capture-confirm. A schema frozen purely for downstream parsing might omit the field the confirm-step needs (e.g. "did *this specific* just-written entry appear?"). *Coordination needed:* design the header once with both consumers at the table; add an `entries_considered` / resolved-id surface the capture-confirm can assert against, versioned so M034/M038 ignore it gracefully.

- **[content-hash freshness contract vs capture-then-immediately-resolve]** — *Their position:* make content-hash (not mtime) the freshness contract because `orchestrator:update`/git-checkout rewrite mtimes wholesale (Rec 9 L83, Missed-Opp L45). *My position:* no objection — but the capture command's round-trip confirmation runs *between* the append and any rebuild, so freshness/staleness must not block or stall the immediate-resolve path (`activation-loop/review.md` L122-125). *Nature of tension:* minor sequencing — a content-hash freshness gate that *blocks* dispatch on stale could, if naively wired, also block the capture-confirm's fresh-write read. *Coordination needed:* the freshness contract governs *dispatch-time* injects; the capture-confirm runs its own targeted grep-over-raw-files independent of the freshness gate (consistent with DQ-3's "rebuild-then-warn" lean, never a hard block on the capture path).

- **[audit-artifact rigor vs three-call-site capture alignment]** — *Their position:* the unguarded-command audit must yield a checked-in artifact enumerating every pipeline in `rebuild-index.sh` + sourced libs (Rec 2 L69). *My position:* the analogous rigor on the capture side is the *three-call-site* alignment — init template header, append script, and consumer awk must all move to the DQ-6 winner in one change set (`activation-loop/review.md` Rec 9 L113-118). *Nature of tension:* none substantive — both are "make the implicit explicit and checkable." *Coordination needed:* model my three-call-site checklist on their audit-artifact pattern: a checked-in assertion that producer, init-header, and consumer agree byte-for-byte on column order, run in CI.

### Safe Agreements

- **[fail-loud is the organizing principle — P-A]** — shared position: pipeline-reliability makes "silent degradation is the enemy; fail loud, never fail open or closed-silent" the spine of the whole FR set (`pipeline-reliability/review.md` L11, L21, Rec 8 L81); my review treats the same fail-loud posture as the property that makes the two-store divergence a *verifiable invariant* rather than a doc note (`activation-loop/review.md` L35: "Leaving it a fork risks shipping the documentation without the enforcement — exactly the fail-open P-A forbids"). *Combined evidence:* the field note's "two milestones, 0-MEM, nobody noticed" is the single ground-truth both perspectives independently cite as the cost of fail-open. *Evidence strength:* high — live production incident, root-caused from two directions. *Confidence: high.*

- **[grep-floor is the guarantee; embeddings only additive — DQ-2]** — shared position: pipeline-reliability's Rec 6 (L77) mandates substring/grep as the deterministic floor and bars embeddings from the corpus-gate evidence artifact; my Rec 10 (`activation-loop/review.md` L120-125) endorses the same grep-floor because the capture command's immediate-resolve confirmation needs deterministic, index-free, same-instant retrieval. *Combined evidence:* their reproducible-trust-receipt argument + my round-trip-confirmation argument are two independent derivations of the same conclusion. *Evidence strength:* strong (two orthogonal rationales converge). *Confidence: high.*

- **[provenance travels in the payload, not stderr-only]** — shared position: pipeline-reliability credits FR-5c for mandating the provenance header *into the injected payload* (`pipeline-reliability/review.md` L27, Alignment L27); my review's system-of-record enforcement (Rec 4) relies on the same payload-resident provenance to make a degraded inject self-declaring. *Combined evidence:* both treat agent-visible provenance as the mechanism that converts "silently under-informed" into "knows it is under-informed." *Evidence strength:* strong. *Confidence: high.*

- **[ship the proven bugs milestone-independent — §7 P0 split is correct]** — shared position: pipeline-reliability endorses §7's carve-out of proven bugs into a milestone-independent P0 hotfix as "the correct blast-radius posture" (`pipeline-reliability/review.md` L11, Rec 11 L87); my review agrees the P0/P1 split is "correct" for the pipeline bugs and disputes only *which capture items* join P0, not the hotfix-independence principle itself (`activation-loop/review.md` L9, L31). *Combined evidence:* both cite §7 L144 ("the proven bugs are actively eroding trust on production projects today") as justification for not waiting on a milestone queue. *Evidence strength:* strong. *Confidence: high* — our only delta is P0 *membership*, not P0 *existence*.
