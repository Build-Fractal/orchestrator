### Executive Summary

The two candidate principles address a structural gap in the current 15-principle constitution: Principles I–XV govern how the orchestrator reasons, builds, and documents, but the constitution is silent on how the orchestrator ships and whether its declared configuration is alive. Candidate A (Distribution Surface Integrity) installs a three-invariant quality gate over every release pathway — single-source versioning, manifest completeness, and end-to-end install smoke. Candidate B (No Dead Infrastructure — config-knob class) extends Principle VIII's file-system reachability floor down to variable-level liveness within declared configuration. Together they form a coherent pair: A guards the outer boundary (what ships to users), B guards the inner boundary (what declared config actually does anything).

Both candidates satisfy the constitution's three inclusion criteria: they each name a mechanical verifier, define a falsifiable scope with hypothetical PR violators, and are distinct from existing principles by a documented scope boundary. Neither candidate's scope overlaps with XI (Single Source of Truth) or VIII (No Dead Infrastructure body-level) in a way that requires one to supersede the other; the overlap is additive, not duplicative.

The weakest dimension in both proposals is that the named mechanical verifiers are currently stubs — "currently a path-existence stub" appears verbatim in Candidate A for all three scripts, and Candidate B's check-dead-infra.sh baseline demonstrates existence rather than adversarial linter coverage. Adopt both candidates, but gate the constitutional ACTIVE status on live verifier promotion within the same milestone that ratifies them.

### Alignment

- **Three-invariant structure with named verifiers** (Candidate A, "Mechanical verification" section): The proposal names three distinct scripts (version-source-of-truth.sh, manifest-coverage.sh, installer-smoke.sh), each with a single-sentence semantics statement ("greps installer scripts for hardcoded version strings; emits PASS / FAIL"). This directly satisfies the constitution's gate definition: "Verification is a mechanical gate, not an LLM compliance exercise. Must-haves... MUST be checkable without human judgment" [`constitution.md`, Principle II, third bullet]. A verifier that greps for hardcoded version strings and emits PASS/FAIL is checkable without human judgment — the pass/fail condition requires no interpretive step.

- **Falsifiable scope with hypothetical PR violators** (Candidate A, "Falsifiable scope" section; Candidate B, "Falsifiable scope" section): Both candidates follow the evidence pattern mandated by Principle II — the hypothetical PR violator is the input, the verifier output is the evidence, and FAIL/PASS is the result. A PR adding `packaging/install/install-jetbrains.sh` with a hardcoded `VERSION="0.9.4"` string would be flagged by version-source-of-truth.sh; a PR adding a new config knob `agent.deliberation.timeout_minutes: 30` with no reader would be flagged by check-dead-infra.sh. Both failure conditions are detectable "without reading any file not referenced in the plan itself" [`constitution.md`, Principle IV]. This is the strongest argument for adoption.

- **Scope boundary documentation** (Candidate B, "Scope boundary" section): Candidate B explicitly states that "config-knob-shaped variables inside `packaging/install/*.sh` installer scripts are outside Candidate B's linter scope." The boundary is recorded in a named artifact (CONFORMANCE.md "Three-bucket structure" table). This boundary-recording practice mirrors the constitution's design gate requirement: "Design artifacts are lightweight and proportional to scope, but they MUST exist" [`constitution.md`, Principle III, fifth bullet]. A principle whose scope boundary is written down and referenced by artifact name passes the principle's own standard.

- **Non-duplication with XI (Single Source of Truth)** (Candidate A, "Distinctness" section): The proposal correctly distinguishes Candidate A's domain (distribution surfaces — installer scripts, bundle manifests, version strings) from XI's domain (orchestrator STATE / CONFIG / KNOWLEDGE). Principle XI's canonical example is that `derive-phase.sh` is the single authoritative state derivation point [`constitution.md`, Principle XI, first bullet]. Candidate A's canonical example is that CHANGELOG.md's top-line `## [X.Y.Z]` heading is the single authoritative version string source. These are orthogonal authoritativeness claims about different artifact classes; adopting A does not weaken XI.

- **Non-duplication with VIII (No Dead Infrastructure body-level)** (Candidate B, "Distinctness" section): Principle VIII governs "every file, script, template, and configuration entry" as FILE-system reachability — audited by run-doctor.sh [`constitution.md`, Principle VIII, second bullet]. Candidate B governs VARIABLE-level liveness within config artifacts — audited by check-dead-infra.sh. These are complementary, non-overlapping surfaces: a config file can be file-system-reachable (passing VIII) while containing dead keys that no reader consumes (violating Candidate B). Adopting B strengthens VIII's coverage without redefining it.

- **Non-duplication with XIV (No Speculative Complexity)** (Candidate B, "Distinctness" section): Principle XIV prohibits implementing UNREQUESTED features [`constitution.md`, Principle XIV, first bullet]. Candidate B prohibits DECLARING config surfaces that are never read. The proposal's own counter-example is precise: "a requested config knob whose reader is later removed but the knob stays declared" violates Candidate B while being fully XIV-compliant (the feature was requested; it was implemented; it was later removed; the declaration was left behind). The failure mode is lifecycle drift, not speculative addition — a genuinely distinct violation class.

### Missed Opportunities

- **Stub-to-live promotion path not specified**: Candidate A names three verifier scripts as "currently a path-existence stub." Principle II requires that verification evidence be fresh and mechanically executable — a path-existence stub passes no behavioral assertion about the thing it claims to verify [`constitution.md`, Principle II, second and third bullets]. The proposal should specify a milestone gate at which each stub must be promoted to a behavioral verifier with a demonstrated FAIL result against a controlled fixture. Without this, the constitutional ACTIVE claim rests on infrastructure that has not been tested against adversarial input. Impact: **high**.

- **Candidate B's "reader" definition is absent**: The proposal states that every entry "MUST have at least one reader in the codebase" but does not define what constitutes a reader. The constitution requires that verifiers "emits PASS / FAIL" in a mechanically checkable way [`constitution.md`, Principle II, third bullet]; a linter whose semantics of "reader" are ambiguous cannot satisfy this requirement. Does a comment referencing the key count? Does a jq expression with a dynamic path? Does a shell `eval` that resolves the key name at runtime? Two independent engineers applying the linter without a reader definition will reach different verdicts. Impact: **high**.

- **"Documented consumer in reference docs" is unlintable**: Candidate B lists "documented consumer in reference docs" as one of the infrastructure entry classes within its linter scope. Reference doc entries are narrative prose — applying check-dead-infra.sh to free-form prose to determine whether a "documented consumer" exists would require NLP-level inference, which the constitution prohibits for mechanical gates [`constitution.md`, Principle II, third bullet]. This entry should be removed from the linter's target set and relocated to the scope boundary exclusion block. Impact: **high**.

- **Line-number reference in Candidate A's statement will become stale**: Candidate A's statement references `packaging/install/install-claude-code.sh:524` as the canonical consumer of the CHANGELOG.md version string. Principle XI requires that knowledge documentation have a single authoritative location [`constitution.md`, Principle XI, first bullet]; a principle text that embeds a line number creates a truth-source conflict with the code the first time the installer is edited. The principle should state the invariant without pinning the consuming line. Impact: **medium**.

- **manifest-coverage.sh fail-open behavior unspecified**: Candidate A invariant 2 does not state what manifest-coverage.sh does when it encounters a bundle directory not present in its known-bundle registry. Principle IX (Reproducibility) requires that identical inputs produce identical outputs [`constitution.md`, Principle IX]. A fail-open verifier that silently passes unknown bundle directories is not reproducible in the adversarial sense — its behavior depends on whether the caller has registered the new bundle. The principle should require fail-closed behavior explicitly. Impact: **medium**.

- **Installer smoke test fixture not pinned**: Candidate A invariant 3 states the smoke test runs "against a fresh project fixture" without specifying whether the fixture is committed or generated ad-hoc. Principle IX requires reproducibility from identical inputs [`constitution.md`, Principle IX]. An ad-hoc fresh directory produces non-deterministic installer environments, meaning the smoke test can pass on a developer's machine and fail in CI against a different filesystem state. Impact: **medium**.

- **No binding criterion (i) verification pathway**: The evaluation directive requires checking whether any membership basis preamble in CONFORMANCE.md grants the project implicit relief from a parent-constitution requirement without routing that relief through a formal Relief pathway. Neither the proposal text nor the provided constitution text surfaces this check; CONFORMANCE.md is cited but not included in the provided files. If the "Three-bucket structure" table in CONFORMANCE.md records either candidate's scope boundary as an implicit relief from a parent principle rather than an independently-grounded distinctness argument, that would constitute a binding criterion (i) failure. The advocate notes this verification gap — it should be resolved before ratification, not after. Impact: **medium**.

### Off-Base Assumptions

- **"Mechanical verification" conflated with "verifier exists"**: The proposal for Candidate A asserts that mechanical verification is satisfied by listing three scripts, each described as "currently a path-existence stub." The constitution's inclusion criteria, as derived from Principle II, require that the verifier actually runs and produces a PASS/FAIL signal on the artifact being checked — not merely that a script file at that path exists [`constitution.md`, Principle II, second bullet: "run the command → read the output → confirm the result matches expectations"]. A path-existence stub satisfies none of this sequence. The proposal conflates "verifier is specified" with "verifier is live." The correct understanding is that constitutional weight should be claimed only after the verifier demonstrates it can flag the hypothetical PR violator described in the proposal.

- **Static linter assumed sufficient for all config reader patterns**: Candidate B's statement that "fully defined, fully typed, fully dead declarations are a defect" implicitly assumes that static analysis of config YAML against script grep patterns is sufficient to determine liveness for all reader patterns in use. In practice, config knobs may be read dynamically — via `eval "key=$config_key"` constructs, via indirect jq expressions, or via shell array expansion. A static linter that does not account for dynamic readers will produce false positives, flagging live knobs as dead. The proposal should acknowledge this limitation and define a "declared reader exception" escape hatch (a CONFORMANCE.md annotation that asserts a dynamic reader exists, satisfying the linter without requiring dynamic analysis). Principle IX (Reproducibility) [`constitution.md`, Principle IX] supports this: the linter's output should be deterministic, which requires a defined resolution for the dynamic-reader case.

### Actionable Recommendations

1. **Require stub-to-live promotion gate before ACTIVE status** (Priority: P1)
   - **Current state**: Candidate A names three verifier scripts, each described as "currently a path-existence stub" in the Mechanical verification section.
   - **Proposed change**: Add a clause: "Each named verifier MUST be promoted from path-existence stub to behavioral verifier — demonstrating at minimum one controlled PASS result and one controlled FAIL result against a committed fixture — before this principle is marked ACTIVE in CONFORMANCE.md. A principle whose verifiers remain stubs is PENDING, not ACTIVE, and does not yet constitute an enforceable gate."
   - **Rationale**: Principle II requires fresh verification evidence before claiming completion [`constitution.md`, Principle II, second bullet]. A stub cannot produce this sequence; constitutional weight claimed prematurely is constitutional weight that cannot be enforced.
   - **Risk if ignored**: A future audit finds the principle is enshrined but its verifiers are stubs. A PR violator passes review because the FAIL condition was never tested. This is the exact class of silent failure Principle II was designed to prevent.

2. **Define "reader" with mechanical precision in Candidate B** (Priority: P1)
   - **Current state**: Candidate B states every entry "MUST have at least one reader in the codebase" without defining reader.
   - **Proposed change**: Add a "Reader definition" clause: "A reader is any of: (a) a direct shell variable assignment consuming the key via `config_get` or equivalent canonical helper, (b) a jq or yq expression that addresses the key by its full YAML path, or (c) a reader-exception entry in CONFORMANCE.md's reader-exception table, which asserts that a dynamic or indirect reader exists and records the dynamic pattern. Comments, reference doc prose, and commit messages are NOT readers."
   - **Rationale**: Principle II requires verifiers to be mechanically checkable without human judgment [`constitution.md`, Principle II, third bullet]. An ambiguous "reader" definition produces verifier results that vary by interpreter, which is a mechanical gate defect.
   - **Risk if ignored**: The linter flags legitimate dynamic readers as dead knobs, producing false-positive failures that erode confidence in the verifier — leading eventually to it being bypassed or gated into advisory-only mode.

3. **Remove "documented consumer in reference docs" from Candidate B's linter scope** (Priority: P1)
   - **Current state**: Candidate B lists "documented consumer in reference docs" as one of four infrastructure entry classes within its linter scope.
   - **Proposed change**: Remove this entry from the scope list and add to the scope boundary exclusion block: "Reference doc entries (prose descriptions of config knobs in `references/` files) are outside Candidate B's linter scope. Their accuracy relative to the config schema is governed by the knowledge-management workflow (Principle VII), not by Candidate B's liveness criterion."
   - **Rationale**: Applying a mechanical linter to free-form prose to determine reader presence requires NLP-level inference, which the constitution prohibits for mechanical gates [`constitution.md`, Principle II, third bullet].
   - **Risk if ignored**: The linter scope covers an artifact class it cannot mechanically verify, producing either systematic false positives (narrative prose is not a "reader") or silent false negatives (the linter skips prose), both of which undermine the principle's enforcement credibility.

4. **Verify binding criterion (i) against CONFORMANCE.md before ratification** (Priority: P1)
   - **Current state**: The evaluation directive requires checking whether CONFORMANCE.md's "Three-bucket structure" table grants implicit relief from a parent-constitution requirement without a formal Relief pathway. CONFORMANCE.md is cited in Candidate B's Distinctness section but is not included in the provided evaluation materials.
   - **Proposed change**: Before ratification, the deliberation record should include a binding criterion (i) verification: read CONFORMANCE.md's Three-bucket structure table and confirm that the scope boundary entries for both candidates are grounded as independently-reasoned distinctness arguments, not as implicit relief from a parent principle. If any entry functions as a relief grant, route it through the constitution's formal amendment pathway before ratification proceeds.
   - **Rationale**: The Governance section requires that amendments include "documented rationale for the change" and "consistency propagation across all dependent templates" [`constitution.md`, Governance section]. A scope boundary that functions as an undocumented relief grant bypasses this pathway.
   - **Risk if ignored**: A future author discovers that one candidate's scope boundary was implicitly granting relief from a parent principle; the constitutional record contains no formal Relief decision; the principle's enforceability in the parent-context case is unclear.

5. **Strip the specific line reference from Candidate A** (Priority: P2)
   - **Current state**: Candidate A's Statement section references `packaging/install/install-claude-code.sh:524` as the current canonical consumer of the CHANGELOG.md version string.
   - **Proposed change**: Replace with "consumed by the installer scripts in `packaging/install/`" — removing the hardcoded line number from the principle text.
   - **Rationale**: Principle XI requires that knowledge documentation have one authoritative location [`constitution.md`, Principle XI]. A principle text that embeds a mutable line number creates a stale-truth risk: the first edit to the installer makes the principle text incorrect.
   - **Risk if ignored**: Within one release cycle the line reference is wrong. Future readers distrust the principle text or spend time auditing a stale line number — a direct violation of Principle I (Context Minimization) for the readers of the constitution itself.

6. **Require fail-closed behavior in manifest-coverage.sh** (Priority: P2)
   - **Current state**: Candidate A invariant 2 does not specify manifest-coverage.sh behavior when it encounters a bundle directory not registered in its known-bundle set.
   - **Proposed change**: Add: "manifest-coverage.sh MUST fail-closed: a bundle directory present in `packaging/bundle/` but absent from the verifier's known-bundle registry MUST produce FAIL with the unknown path listed, not a silent PASS. This prevents new runtime adapters from bypassing the force-include discipline by not being registered."
   - **Rationale**: Principle IX (Reproducibility) requires that identical inputs produce identical outputs [`constitution.md`, Principle IX]. A fail-open verifier whose behavior depends on the caller's registration is not reproducible in the adversarial sense.
   - **Risk if ignored**: A new runtime adapter ships with files not listed in its manifest. The verifier silently passes. The violation surfaces only at the first real-user install attempt.

7. **Pin installer smoke test fixture as a committed artifact** (Priority: P2)
   - **Current state**: Candidate A invariant 3 states the smoke test runs "against a fresh project fixture" without specifying whether the fixture is committed or ad-hoc.
   - **Proposed change**: Add: "The 'fresh project fixture' MUST be a committed fixture directory or a deterministic generation script producing byte-identical output, located under `tests/fixtures/install-smoke/`. Ad-hoc freshly-generated directories are not acceptable: they produce non-deterministic installer environments that violate Principle IX (Reproducibility)."
   - **Rationale**: Principle IX requires identical outputs from identical inputs [`constitution.md`, Principle IX]. An ad-hoc fixture is not an identical input across environments.
   - **Risk if ignored**: The smoke test passes on a developer's machine with a particular filesystem state and fails in CI with a different state. The gate is not a reliable enforcement surface.

8. **Add a joint scope table in CONFORMANCE.md for the A/B boundary** (Priority: P3)
   - **Current state**: Candidate A excludes installer-script config-knob-shaped variables from Candidate B's scope. Each candidate's Scope boundary section states this, but there is no single table that makes the boundary navigable to a reviewer applying both principles simultaneously.
   - **Proposed change**: Add a "Two-principle boundary" row to CONFORMANCE.md's Three-bucket structure table, and append to both candidates' Scope boundary sections: "For the authoritative boundary between Candidate A (distribution surface integrity) and Candidate B (config-knob liveness), see the 'Two-principle boundary' row in CONFORMANCE.md. That table is the single source of truth for boundary disputes."
   - **Rationale**: Principle XI (Single Source of Truth) — "every piece of orchestrator state, configuration, and knowledge MUST have exactly one authoritative location" [`constitution.md`, Principle XI]. Two principles that share a boundary need one document to own that boundary's definition.
   - **Risk if ignored**: A future PR at the installer/config boundary is evaluated differently by two reviewers applying the principles independently, producing an enforcement inconsistency that cannot be resolved by reading either principle text alone.
