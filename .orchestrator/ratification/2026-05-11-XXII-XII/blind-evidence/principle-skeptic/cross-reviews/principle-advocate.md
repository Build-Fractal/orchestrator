### Dangerous Contradictions

- **[Candidate A Distinctness from XI: acceptance vs. rejection]**
  - **principle-advocate claims**: "The proposal correctly distinguishes Candidate A's domain (distribution surfaces — installer scripts, bundle manifests, version strings) from XI's domain (orchestrator STATE / CONFIG / KNOWLEDGE). These are orthogonal authoritativeness claims about different artifact classes; adopting A does not weaken XI." (principle-advocate, "Alignment — Non-duplication with XI" section)
  - **principle-skeptic claims**: "Principle XI's normative body does not support this restriction: 'Every piece of orchestrator state, configuration, and knowledge MUST have exactly one authoritative location. Duplication across files is a consistency bug waiting to happen.' A version string hardcoded in multiple installer scripts is configuration. Its duplication across files is precisely what XI prohibits. The scope restriction is not in XI's text." (principle-skeptic, "Off-Base Assumptions — Principle XI's scope excludes installer-script version strings")
  - **Why this is dangerous**: The two reviews reach opposite verdicts on Candidate A's most fundamental distinctness claim. If the advocate's position is adopted, Candidate A earns full constitutional standing and Invariant 1 becomes an enforceable constitutional requirement. If the skeptic's position is adopted, Invariant 1 must be reassigned to XI enforcement and Candidate A may not survive as an independently-ratifiable principle. Implementing both positions simultaneously produces a constitutional corpus where XI is simultaneously narrow (advocate's reading: doesn't reach installer scripts) and broad (skeptic's reading: already covers them), making it impossible for a future maintainer to determine which principle governs a version-string duplication violation in an installer.
  - **Suggested resolution**: The arbiter must take a textual position on XI's normative body. The critical question is whether "configuration" in XI's phrase "state, configuration, and knowledge" includes installer script content or is restricted to orchestrator runtime config artifacts. The skeptic's argument is stronger because XI's normative body names no such restriction and explicitly says "duplication across files is a consistency bug" without carving out installer scripts. The advocate should yield on this point: Invariant 1 belongs as a named XI-enforcement script, not a constitutional invariant. The advocate's broader adoption recommendation can survive if Invariants 2 and 3 are independently grounded — which requires resolving the next contradiction.

- **[Invariant 3 structural home: constitutional invariant vs. quality gate]**
  - **principle-advocate claims**: Accepts all three invariants and recommends adopting Candidate A with a stub-to-live promotion gate before ACTIVE status. The advocate's eight recommendations do not include reclassifying Invariant 3 — they address stub promotion, fixture pinning, and fail-closed behavior, all of which treat Invariant 3 as a constitutional requirement that needs operational tightening. (principle-advocate, "Actionable Recommendations" #1, #7)
  - **principle-skeptic claims**: "Invariant 3 is a Quality Gate masquerading as a constitutional invariant. End-to-end install testing at every release gate is release evidence, not an architectural mandate. The correct structural home is a named gate entry in the Quality Gates section, not an invariant in a constitutional principle." (principle-skeptic, "Missed Opportunities — Invariant 3 reclassification as a Quality Gate"; recommendation #2)
  - **Why this is dangerous**: These positions assign Invariant 3 to different enforcement namespaces with different governance semantics. Constitutional principles govern architectural mandates and are amended via the versioned Governance pathway. Quality gate entries govern release evidence and are updated procedurally. If the advocate's position is adopted, Invariant 3 is constitutional and can only be relaxed via a MINOR or MAJOR amendment with version bump and documented rationale. If the skeptic's position is adopted, the same requirement lives in the Quality Gates section and can be updated as a PATCH. The confusion surfaces when a future engineer tries to relax the smoke test requirement — they will find contradictory guidance about which section governs and which amendment pathway applies.
  - **Suggested resolution**: The skeptic's structural argument is more precise. The constitution's own Quality Gates section already states "No phase advances without verification evidence" as its governing mandate — end-to-end install testing is exactly this kind of release evidence. The advocate should yield on Invariant 3's structural home while preserving the substantive requirement: move Invariant 3 to Quality Gates and specify "version-tag publication" (the skeptic's named trigger from recommendation #2) as the triggering condition. The substantive enforcement — that install paths must be smoke-tested before release — survives intact in either structural home; only the amendment pathway changes.

- **[Candidate B and Principle VIII's "configuration entry" — accepted distinctness vs. open dispute]**
  - **principle-advocate claims**: "Principle VIII governs 'every file, script, template, and configuration entry' as FILE-system reachability — audited by run-doctor.sh. Candidate B governs VARIABLE-level liveness within config artifacts — audited by check-dead-infra.sh. These are complementary, non-overlapping surfaces." (principle-advocate, "Alignment — Non-duplication with VIII" section)
  - **principle-skeptic claims**: "Principle VIII's text enumerates 'configuration entry' as a distinct noun from 'file.' If 'configuration entry' meant 'the config file,' it would be redundant with 'file.' The natural reading is that 'configuration entry' means an individual entry — a variable-level unit — within a config artifact. If that reading is correct, Candidate B is a scope-narrowed restatement of VIII, not a distinct principle." (principle-skeptic, "Off-Base Assumptions — Principle VIII's 'configuration entry' means a config file, not a config knob"; Dispute D-B1)
  - **Why this is dangerous**: The advocate accepts Candidate B's distinctness from VIII as settled and recommends adoption; the skeptic treats it as an open question requiring a PATCH amendment to VIII before Candidate B can be admitted. If the advocate's position is adopted without the skeptic's prerequisite amendment, the constitutional corpus contains two principles whose scope overlap is unresolved by any authoritative text. A future maintainer applying both principles to the same dead config knob will find VIII and Candidate B offering competing enforcement surfaces (run-doctor.sh vs. check-dead-infra.sh) with no declared hierarchy. The ambiguity is not resolvable from the principle texts alone.
  - **Suggested resolution**: The skeptic's prerequisite — a PATCH amendment to VIII clarifying "'configuration entry' means a configuration artifact as a file-system object, not an individual entry within that artifact" — is the correct resolution path. The advocate should acknowledge this as a precondition for Candidate B's ratification rather than treating the distinctness as already established. The amendment is low-effort (PATCH, no version-bump ceremony required beyond documentation) and resolves the ambiguity permanently. Both reviews agree on the substantive concern; the dispute is only about whether the clarification must happen before or after ratification.

- **[Threshold for constitutional standing: "adopt and gate" vs. "reform before admitting"]**
  - **principle-advocate claims**: "Adopt both candidates, but gate the constitutional ACTIVE status on live verifier promotion within the same milestone that ratifies them." The advocate treats constitutional inclusion as separable from verifier liveness — a principle can be ratified as PENDING and then promoted to ACTIVE once verifiers are live. (principle-advocate, Executive Summary)
  - **principle-skeptic claims**: The skeptic's recommendations require structural reforms (Invariant 1 reassignment, Invariant 3 reclassification, VIII PATCH amendment, Candidate B scope narrowing) before ratification, not after. The implicit position is that constitutional standing should not be granted to a principle that requires material structural changes — because once ratified, the reform requires amending the constitution, not just updating a CONFORMANCE.md status field. (principle-skeptic, recommendations #1–#5, all Priority: P1)
  - **Why this is dangerous**: The "adopt and gate" model creates constitutional debt: principles are ratified in a form that both reviews agree requires reform, and the reforms are deferred to an unspecified milestone. Constitutional debt compounds — each subsequent milestone that inherits the constitution inherits the unreformed principles, and the structural changes (reassigning Invariant 1 to XI enforcement, moving Invariant 3 to Quality Gates) become progressively more disruptive to enforce because dependent templates and enforcement scripts have already been written against the pre-reform text. The "reform before admitting" model prevents this but delays ratification.
  - **Suggested resolution**: A hybrid: ratify the reforms as preconditions, then ratify the narrowed candidates in a single milestone. This preserves the advocate's timeline goal (both candidates ratified in one pass) while incorporating the skeptic's structural corrections before they become load-bearing text. The preconditions are: (1) Invariant 1 reassigned to XI compliance notes; (2) Invariant 3 moved to Quality Gates; (3) VIII PATCH amendment issued; (4) Candidate B normative scope narrowed to one demonstrated class with extension clause. These are edit-level changes that do not require a new deliberation cycle.

### Tensions

- **[Stub verifiers: feasibility gate vs. sufficiency gate]**
  - **principle-advocate's position**: Treats stub acknowledgment as satisfying the constitutional bar for inclusion because "the constitutional bar for inclusion is verification *feasibility*, not current implementation completeness." The advocate's P1 recommendation #1 adds a PENDING/ACTIVE distinction that gates ACTIVE status on live verifier promotion, but allows ratification to proceed. (principle-advocate, "Alignment — Explicit stub acknowledgment"; recommendation #1)
  - **principle-skeptic's position**: Treats stub acknowledgment as honest but insufficient: "A path-existence stub satisfies none of this sequence [run the command → read the output → confirm the result matches expectations]." The skeptic's cross-tier checklist criterion (iii) further distinguishes feasibility from sufficiency: "Stub paths that exist but emit 'TODO' satisfy Criterion 1 feasibility but NOT Criterion 3 sufficiency." (principle-skeptic, "Off-Base Assumptions — 'Mechanical verification' conflated with 'verifier exists'"; Disputes section cross-tier checklist)
  - **Nature of tension**: Both reviews correctly identify the distinction between feasibility and sufficiency, but draw the ratification gate in different places. The advocate gates ACTIVE (enforcement) on live verifiers but allows ratification (constitutional text) to proceed with stubs. The skeptic implies ratification should wait until the reforms are complete, which — given the stub state — would also require live verifiers before the ratification milestone closes. These are not mutually exclusive positions: the advocate's PENDING/ACTIVE distinction could satisfy the skeptic if the PENDING state explicitly carries no enforcement weight and the ACTIVE promotion requires demonstrated FAIL results against controlled fixtures.
  - **Coordination needed**: The ratification record should explicitly define what PENDING means: "A PENDING principle establishes normative intent but is not a mechanical enforcement gate. PRs are not blocked on PENDING principle violations. ACTIVE status requires demonstrated PASS+FAIL results from live verifiers against committed fixtures, declared in CONFORMANCE.md." This formalization would allow the advocate's timeline (ratify now) and the skeptic's enforcement standard (no false mechanical gates) to coexist.
