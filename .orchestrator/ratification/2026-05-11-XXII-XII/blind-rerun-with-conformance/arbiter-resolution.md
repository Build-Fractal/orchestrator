#### Dispute: Definition Precision for "Fresh Project Fixture"

**Positions:**
- **Principle-advocate** (Surviving Rec 2, Phase 3 Revision): "a temporary directory containing only the minimum files required by the runtime's project layout, with no pre-existing `.orchestrator/` directory."
- **Principle-skeptic** (Dispute 2, Phase 4): base definition — "a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state" — plus explicit escape hatch: "where a runtime requires pre-existing scaffold files before the installer can be invoked, those files MUST be enumerated explicitly in the smoke test fixture's documented preconditions and MUST NOT overlap with any file that the installation itself places."

**Synthesizer's assessment:** The skeptic's position is analytically stronger and should be adopted. The advocate's formulation imports exactly the judgment it was designed to eliminate. The skeptic's base definition is mechanically deterministic: run the installer, observe the file system diff. The escape hatch mechanism is the architecturally correct response to the scaffold edge case — make the accommodation explicit and auditable, not implicit. (Synthesis, Remaining Disputes §3, Synthesizer assessment.)

**Ruling:** Adopt the skeptic's two-part resolution. The base definition is: "A fresh project fixture is a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state. The fixture is created immediately before and destroyed immediately after each release gate run." The escape hatch is: "Where a runtime requires pre-existing scaffold files before the installer can be invoked, those files MUST be enumerated explicitly in the smoke test fixture's documented preconditions and MUST NOT overlap with any file that the installation itself places. A fixture specification that requires runtime-specific preconditions must document those preconditions in a named fixture manifest file within `scripts/verify/`."

**Grounding citation:** Principle II (Evidence Before Claims): "Verification is a mechanical gate, not an LLM compliance exercise. Must-haves MUST be checkable without human judgment." The operative test: can `installer-smoke.sh` determine PASS/FAIL deterministically from the definition? The advocate's definition requires determining what constitutes "minimum files required by the runtime's project layout" — this is a knowledge-dependent judgment, not a deterministic observation. The skeptic's definition requires observing what files the installer placed — this is a deterministic observation. Only the latter satisfies Principle II's mechanical-gate requirement.

**Rationale:** The purpose of defining "fresh project fixture" is not to describe the fixture philosophically — it is to specify the input to `installer-smoke.sh` precisely enough that the script can construct the fixture without human guidance. The advocate's formulation fails this test at the word "minimum": no script has access to a canonical definition of what "minimum" means for an arbitrary runtime's project layout, and the definition does not specify where that definition would be found. The skeptic's formulation succeeds: create an empty directory, run the installer, the resulting file system state is the fixture. The escape hatch pattern the skeptic proposes is not a weakness — it is architecturally superior to the advocate's approach because it makes runtime-specific accommodations explicit and auditable rather than implicit in the base term. An explicit fixture manifest file within `scripts/verify/` for runtimes requiring scaffold preconditions is machine-readable and reviewable; "minimum files required by the runtime's project layout" is not.

**Rejected position:** The advocate's formulation was designed to accommodate the legitimate case where a runtime (e.g., one requiring an existing `package.json` scaffold) cannot be installed into a fully empty directory. This concern is valid. The advocate's method of accommodating it — encoding the accommodation into the base definition — is not. Encoding flexibility into a base definition that is supposed to be mechanically deterministic produces exactly the interpretive ambiguity that the definition was authored to eliminate. The correct mechanism is the skeptic's escape hatch: the accommodation is allowed, but it must be explicit, named, and auditable. The advocate's strongest argument ("minimum files required by the runtime's project layout" accommodates the scaffold case) applies equally to the skeptic's named-preconditions escape hatch, which accommodates the scaffold case while remaining objectively deterministic for the default case.

**Required changes:** In the pre-ratification Invariant 3 text amendment (required per Dispute 1 ruling), use the following exact wording for the "fresh project fixture" definition — this is the authoritative formulation and supersedes the advocate's Surviving Rec 2 wording:

> A fresh project fixture is a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state. The fixture is created immediately before and destroyed immediately after each release gate run. Where a runtime requires pre-existing scaffold files before the installer can be invoked, those files MUST be enumerated explicitly in the smoke test fixture's documented preconditions and MUST NOT overlap with any file that the installation itself places. A fixture specification that requires runtime-specific preconditions must document those preconditions in a named fixture manifest file within `scripts/verify/`.

This definition is inserted into Candidate A's Invariant 3 description alongside the "works" definition. Both definitions together constitute the pre-ratification Invariant 3 text amendment required by the Dispute 1 ruling.
