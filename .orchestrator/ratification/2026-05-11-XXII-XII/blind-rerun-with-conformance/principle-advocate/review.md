### Executive Summary

Both candidate principles address genuine gaps in the current constitution. Candidate A (Distribution Surface Integrity) governs the installer and bundle-manifest layer — a class of artifacts that Principle XI (Single Source of Truth) names at the domain level of state, configuration, and knowledge, but does not reach at the depth needed to prevent installer version drift, un-manifested bundle files, or untested install paths. Candidate B (No Dead Infrastructure, config-knob class) governs variable-level liveness within configurable infrastructure artifacts — a scope that Principle VIII (No Dead Infrastructure, file-system level) explicitly does not reach. Both candidates satisfy the three inclusion criteria: mechanical verification feasibility is demonstrated by named scripts (Candidate A: three stubs with deterministic, greppable logic; Candidate B: a live linter with a documented and numerically-specific baseline), falsifiable scope is demonstrated by concrete PR-violator examples requiring no interpretation, and distinctness is demonstrated by cases where a violation of each candidate would not be caught by any existing principle.

The case for Candidate A is strongest in Invariants 2 and 3: force-include discipline (un-manifested bundle files) and end-to-end install testing have no analog anywhere in the current constitution. Invariant 1 (single-source versioning) sits closest to Principle XI and will attract a distinctness challenge — that challenge is answerable, but the advocate must be precise: XI governs the canonical location of STATE/CONFIG/KNOWLEDGE artifacts, not the derivation chain of version strings embedded in installer scripts. The case for Candidate B is the stronger of the two: the linter already exists, the baseline is documented ("0 dead leaves across 41 leaves"), and the scope boundary from Principle VIII is precisely articulated with separate canonical audit tools assigned to each layer.

My most important recommendation: adopt both candidates, but require Candidate A's three verification stubs to reach ACTIVE implementation status before the principle's mechanical verification criterion is marked Satisfied — path-existence alone does not constitute the evidence standard Principle II demands.

### Alignment

- **Candidate A's PR-violator examples are interpretation-free** (inheritance-claims-blind.md, Falsifiable scope section for Candidate A): The proposal supplies three concrete examples — a new installer with `VERSION="0.9.4"` hardcoded, a new bundle file absent from `manifest.txt`, a broken curl-pipe-bash install path — each of which a verifier can flag without human judgment. This meets the Governance section's "falsifiable scope" criterion exactly as stated [`.orchestrator/memory/constitution.md`, Governance section: "three tests (mechanical verification capability / falsifiable scope / distinctness)"]. A principle whose enforcement requires interpretation is unenforceable; Candidate A's three examples are enumerable and automatable.

- **Candidate A's one-script-per-invariant mapping is architecturally clean** (inheritance-claims-blind.md, Mechanical verification section for Candidate A): `version-source-of-truth.sh` covers Invariant 1 (grep installer scripts for hardcoded version strings), `manifest-coverage.sh` covers Invariant 2 (diff bundle directory against `manifest.txt`), `installer-smoke.sh` covers Invariant 3 (run each installer against a fresh project fixture). Each script maps to one invariant class, each script produces PASS/FAIL output, each script has a deterministic algorithm. This satisfies Principle II's requirement that verification be "a mechanical gate, not an LLM compliance exercise" [`.orchestrator/memory/constitution.md`, Principle II].

- **Candidate B's existing linter and documented baseline constitutes run-evidence, not merely feasibility** (inheritance-claims-blind.md, Mechanical verification section for Candidate B): "Baseline 2026-05-11: 0 dead leaves across 41 leaves in `templates/orchestrator-config-default.yml`" is a run result, not a feasibility claim. The linter exists, has been executed, and produced a numbered baseline. This is the strongest mechanical verification evidence of either candidate — it satisfies Principle II at the "run the command → read the output → confirm the result" standard [`.orchestrator/memory/constitution.md`, Principle II].

- **Candidate B's scope boundary from Principle VIII is precisely articulated** (inheritance-claims-blind.md, Scope boundary section for Candidate B): The proposal correctly identifies that file-system reachability of helper scripts and reference doc files is Principle VIII's domain (canonical audit: `run-doctor.sh`) and config-knob liveness is Candidate B's domain (canonical linter: `check-dead-infra.sh`). This decomposition fills the variable-level gap that Principle VIII explicitly does not address — "Every file, script, template, and configuration entry MUST be reachable from a live code path" names artifact reachability, not variable-level liveness within configurable infrastructure [`.orchestrator/memory/constitution.md`, Principle VIII].

- **Candidate B's XIV distinctness case is rigorous** (inheritance-claims-blind.md, Distinctness section for Candidate B): "A future implementer can violate Candidate B without violating XIV (e.g., a requested config knob whose reader is later removed but the knob stays declared)." This is a precise counterexample: XIV prohibits implementing unrequested features [`.orchestrator/memory/constitution.md`, Principle XIV: "Every implementation MUST deliver exactly what was requested — nothing more"]; Candidate B prohibits retaining declared config surfaces after their readers are removed. The two are orthogonal — a single PR can violate one without violating the other, which is the strongest possible distinctness demonstration.

- **Both candidates name their verifier tools at concrete `scripts/` paths** (inheritance-claims-blind.md, Mechanical verification sections for both): Every verifier is identified by a specific path under `scripts/`, which is the project's established pattern for mechanical audit tooling. This makes the verification chain inspectable, runnable, and auditable — consistent with the pattern established by `scripts/diagnostics/run-doctor.sh` for Principle VIII and `scripts/diagnostics/check-dead-infra.sh` for Candidate B.

### Missed Opportunities

- **Candidate A does not specify where in the release pipeline each verifier fires**: The proposal states verifiers "emit PASS / FAIL" but does not specify the gate point — pre-commit hook, CI lint step, or release-time gate (inheritance-claims-blind.md, Mechanical verification section for Candidate A). Invariant 3's smoke test is heavyweight and inappropriate for pre-commit; Invariants 1–2 are lightweight and appropriate for CI. Without gate-point specification, "end-to-end install testing" is aspirational rather than gated. Principle IX (Reproducibility) requires that orchestrator operations with identical inputs produce identical outputs [`.orchestrator/memory/constitution.md`, Principle IX]; a verifier that fires inconsistently across teams and environments is not reproducible. **Impact: high.** Candidate A should specify: Invariants 1–2 fire as CI lint steps; Invariant 3 fires at release tag time.

- **Candidate A's "future runtime-adapter installer" clause has no registration mechanism**: The statement names three current installer paths but says the three invariants apply to "any future runtime-adapter installer" without specifying how verifiers know a new installer exists (inheritance-claims-blind.md, Statement section for Candidate A). If `version-source-of-truth.sh` hardcodes the three current paths, adding `install-jetbrains.sh` places it outside the verifier's scope. Principle XI (Single Source of Truth) requires one authoritative location — that location should be the `packaging/install/` directory listing itself, not a hardcoded list inside the verifier [`.orchestrator/memory/constitution.md`, Principle XI]. **Impact: high.** The principle should specify that verifiers enumerate `packaging/install/install-*.sh` dynamically.

- **Candidate B's frontmatter config option scope is declared in scope but explicitly undrawn**: "SKILL.md-equivalent config options declared in command frontmatter" are listed as in scope, but the scope boundary note immediately follows: this bucket is PENDING — scope not yet drawn (CONFORMANCE.md, Tier 2 XII clause-mapping scaffold, row 3). A principle with an explicitly-undrawn scope cannot pass/fail a PR deterministically. The mechanical verification criterion requires defined scope; "PENDING" is an admissible status for a clause-mapping scaffold, but it is not admissible in a principle statement that declares the bucket in scope. **Impact: high.** Either draw the frontmatter scope explicitly in the principle text, or narrow Candidate B's declared scope to `templates/orchestrator-config-default.yml` config knobs and defer the frontmatter bucket to a follow-on amendment.

- **Neither candidate specifies a violation remediation protocol**: Both candidates specify verifier output (PASS/FAIL) but neither specifies what happens when a violation is found — who remediates, within what timeframe, and how the remediation is recorded. Principle VI (State On Disk Is Truth) requires that all state be recoverable from disk [`.orchestrator/memory/constitution.md`, Principle VI: "If it is not on disk, it did not happen. No exceptions."]. A violation acknowledged verbally and remediated without a disk-persisted record is invisible to future auditors and to crash recovery. **Impact: medium.** Both candidates should specify that violations are recorded as FAIL events (per Principle II's `emit_event` requirement) and that unresolved violations are tracked in CONFORMANCE.md's Provisional remediation plan table with a named deadline.

- **Candidate A's Invariant 2 does not specify the `manifest.txt` format**: "New files require manifest update; CI fails on un-manifested includes" — but `manifest.txt`'s format (does it allow comments? is it order-sensitive? does it support globs?) determines what `manifest-coverage.sh` must handle (inheritance-claims-blind.md, Statement section for Candidate A, Invariant 2). A verifier whose input format is underspecified is not reproducible across implementations. **Impact: medium.** Invariant 2 should reference the existing format in `packaging/bundle/<runtime>/manifest.txt` or specify it inline.

- **Candidate A does not address distinctness from Principle X**: Principle X (Templating Over Inference) declares that "configuration and policy MUST be declared in templates, not inferred by scripts at runtime" [`.orchestrator/memory/constitution.md`, Principle X]. Invariant 2 (force-include discipline) could be read as a special case of X applied to bundle manifests — the manifest is the "template" that declares what ships. Candidate A's Distinctness section addresses XI but not X. This gap is answerable (A governs whether distribution artifacts match their manifests; X governs whether policy is declared in templates rather than inferred at runtime — orthogonal domains), but leaving a plausible overlap unaddressed provides the skeptic a clean challenge. **Impact: low.** Add one sentence to Candidate A's Distinctness section addressing X explicitly.

- **Candidate B does not specify a grandfathering protocol for pre-existing dead config knobs**: The baseline is documented at 0 dead leaves for this specific project, but a principle intended for general adoption must handle projects that start with N dead leaves (inheritance-claims-blind.md, Mechanical verification section for Candidate B). The CONFORMANCE.md Provisional remediation plan table provides exactly the right venue for deadline-tracked open audits (CONFORMANCE.md, Provisional remediation plan section). **Impact: low.** Candidate B should specify that pre-existing dead knobs at adoption time are tracked in CONFORMANCE.md with a remediation deadline, following the existing Provisional audit pattern.

### Off-Base Assumptions

- **Candidate A assumes path-existence stubs constitute demonstrated mechanical verification feasibility**: All three of Candidate A's verifiers are described as "currently a path-existence stub" (inheritance-claims-blind.md, Mechanical verification section for Candidate A). The proposal presents this as satisfying the mechanical verification criterion by demonstrating that the verification chain is "feasibility"-proven. But Principle II requires: "run the command → read the output → confirm the result matches expectations" [`.orchestrator/memory/constitution.md`, Principle II]. A script that exists but does not yet run produces no output and cannot confirm any result. Path-existence is evidence of intent, not feasibility. The correct understanding: the scripts' algorithmic structure (grep for hardcoded strings, diff directories, run installer) is deterministic enough to be clearly implementable — this is the actual feasibility argument, and it is valid. But it should be stated as an implementation-readiness claim, not as equivalent to a working verifier. The mechanical verification criterion for Candidate A is at PENDING status, not Satisfied, until all three scripts produce PASS/FAIL output.

- **Candidate B's "documented consumer in reference docs" clause conflates documentation with readership**: The proposal states that a config knob is not dead if it has "at least one reader in the codebase" and lists "documented consumer in reference docs" as one of the covered surfaces (inheritance-claims-blind.md, Statement section for Candidate B). A reference doc that describes a config knob is not a reader of it — it is documentation about it. Whether describing a knob in a reference doc constitutes "reading" it is an interpretation question, which contradicts the falsifiable-scope criterion requiring that "a reader can determine pass/fail mechanically without interpretation" (inheritance-claims-blind.md, Falsifiable scope section for Candidate B). The mechanically-checkable case (a shell script that reads a config value via `yq` or `grep`) satisfies the falsifiability standard cleanly; the reference-doc case does not. The CONFORMANCE.md clause-mapping scaffold already labels this bucket PENDING and Provisional — but the principle statement does not reflect this caveat, creating an expectation gap between the principle's declared scope and its actual enforced scope. The correct understanding: Candidate B's falsifiable scope is robustly demonstrated for the config-knob-to-script-reader surface; the reference-doc reader surface requires a scoping decision that is not yet made and should not be declared in scope before it is.

- **Criterion (i) check — the Independence Argument is structurally distinct from implicit Relief, but its interpretation depends on how SOURCE B's Purpose-clause prerequisites are typed**: The CONFORMANCE.md Tier 2 Inheritance Basis explicitly acknowledges that orchestrator does not satisfy SOURCE B's three Purpose-clause structural prerequisites (multi-agent deliberation substrate, plugin entry-point boundary shape, free/paid partition) and argues that XXII and XII remain applicable because their normative bodies are domain-specific and independent of those prerequisites (CONFORMANCE.md, Tier 2 Inheritance Basis, Paragraphs 1–3). The document explicitly disclaims the Relief pathway: "NOT on a path (a) feature-mapping-with-Relief-invocation." The criterion (i) check asks: does this grant implicit relief without the formal pathway? The answer turns on how SOURCE B's three prerequisites are typed. If they are **purpose-clause prerequisites** — describing the architectural context in which the Tier 2 suite constitution was authored — then they do not universally gate all Tier 2 principle inheritance; the Independence Argument correctly identifies which principles' normative bodies are prerequisite-independent. If they are **membership-eligibility gates** — universally gating all Tier 2 inheritance regardless of principle scope — then the Independence Argument is a structural end-run around the formal Relief pathway. As advocate: the Independence Argument holds on the purpose-clause reading, and the three principles' normative bodies (installer-domain scope for XXII; config-knob scope for XII) demonstrably do not reference deliberation substrates, plugin boundaries, or revenue models. The criterion (i) check passes on this reading. However, this ambiguity should be resolved before the amendment is finalized — the amendment should state explicitly whether SOURCE B's prerequisites are purpose-clause or membership-eligibility typed, so future amendments cannot re-litigate this question on different readings.

### Actionable Recommendations

1. **Require ACTIVE implementation for Candidate A's three stubs before marking Satisfied** (Priority: P1)
   - **Current state**: All three verifiers are "currently a path-existence stub" (inheritance-claims-blind.md, Mechanical verification section for Candidate A). Path-existence proves verification intent, not verification capability.
   - **Proposed change**: Add a status note to Candidate A's Mechanical verification section: "Invariants (1)–(3) are at PENDING verification status until the respective scripts produce structured PASS/FAIL output for a representative installer fixture. The principle's mechanical verification criterion is Satisfied only when all three scripts emit structured pass/fail results on each release gate run." Adopt the three-bucket vocabulary (Satisfied / Provisional / Extended) from CONFORMANCE.md for tracking.
   - **Rationale**: Principle II (Evidence Before Claims) — "'Should work' is NOT evidence" [`.orchestrator/memory/constitution.md`, Principle II]. The inclusion criteria require mechanical verification capability, not mechanical verification intent. Stub existence proves the verification chain is planned; only a running script with documented output proves it is capable.
   - **Risk if ignored**: Candidate A is ratified with the understanding that enforcement is imminent. If any stub proves harder to implement than expected — for example, `installer-smoke.sh` requires runtime fixture infrastructure not yet built — the principle enters the constitution without enforcement, which is documentation debt that grows across every future release.

2. **Define "fresh project fixture" in Candidate A's Invariant 3** (Priority: P1)
   - **Current state**: Invariant 3 states "every release gate runs each per-runtime installer against a fresh project fixture" but does not define what constitutes such a fixture (inheritance-claims-blind.md, Statement section for Candidate A, Invariant 3).
   - **Proposed change**: Add a fixture definition: "A fresh project fixture is a temporary directory containing only the minimum files required by the runtime's project layout, with no pre-existing `.orchestrator/` directory. The fixture is created immediately before and destroyed immediately after each release gate run. A fixture that retains state from a prior run is not a fresh fixture."
   - **Rationale**: Principle IV (Plans Assume Zero Context) — plans must not require the executor to "figure it out" [`.orchestrator/memory/constitution.md`, Principle IV]. Two release engineers with different interpretations of "fresh" will produce different verifier results. An undefined fixture is a non-reproducible test.
   - **Risk if ignored**: `installer-smoke.sh` passes on one machine (where the fixture happens to be clean) and fails on another (where a prior install left artifacts). Invariant 3 provides false assurance about cross-environment reliability.

3. **Draw the SKILL.md-equivalent frontmatter scope for Candidate B before adoption** (Priority: P1)
   - **Current state**: "SKILL.md-equivalent config options declared in command frontmatter" are listed in Candidate B's scope with the boundary explicitly undrawn (CONFORMANCE.md, Tier 2 XII clause-mapping scaffold, row 3: "PENDING — scope not yet drawn").
   - **Proposed change**: Either (a) draw the scope in Candidate B's principle text, specifying which frontmatter keys are governed by `check-dead-infra.sh` and how the linter reads command files, or (b) explicitly narrow Candidate B's declared scope to "config knobs in `templates/orchestrator-config-default.yml`" and defer the frontmatter bucket to a follow-on amendment with an explicit timeline.
   - **Rationale**: A principle with a declared-but-undrawn scope creates an enforcement dispute that cannot be resolved mechanically. The falsifiable-scope criterion requires that "a reader can determine pass/fail mechanically without interpretation" (inheritance-claims-blind.md, Falsifiable scope section for Candidate B); this is not possible for a scope whose boundary has not been drawn.
   - **Risk if ignored**: An author adds a config option to command frontmatter. One reviewer flags it as a Candidate B violation. Another reviewer says it is outside scope. No authoritative resolution exists within the principle text, and the dispute must escalate to governance — the opposite of what a falsifiable principle should require.

4. **Add explicit distinctness argument against Principle X to Candidate A** (Priority: P2)
   - **Current state**: Candidate A's Distinctness section addresses Principle XI but does not address Principle X (Templating Over Inference), despite Invariant 2 (force-include discipline) being plausibly readable as X applied to bundle manifests (inheritance-claims-blind.md, Distinctness section for Candidate A).
   - **Proposed change**: Add one sentence to Candidate A's Distinctness section: "Distinct from existing Principle X (Templating Over Inference): Principle X governs whether policy is declared in templates rather than inferred at runtime; Candidate A governs whether distribution artifacts on disk match their declared manifests at ship time. X constrains the configuration architecture of scripts; A constrains the completeness of release artifacts. A PR can satisfy X (all policy is template-declared) while violating A (a template-declared file is missing from the manifest)."
   - **Rationale**: The inclusion criteria require distinctness from existing principles [`.orchestrator/memory/constitution.md`, Governance section]. An unaddressed plausible overlap provides the skeptic a clean inclusion-criteria challenge at cross-review. The argument is straightforward to make; it is better to make it proactively.
   - **Risk if ignored**: Cross-review surfaces the X overlap as an unaddressed inclusion-criteria gap. The amendment is remanded for additional distinctness argument, delaying ratification.

5. **Specify CI/release gate integration points for Candidate A's three verifiers** (Priority: P2)
   - **Current state**: The proposal says verifiers "emit PASS / FAIL" but does not specify when they are invoked (inheritance-claims-blind.md, Mechanical verification section for Candidate A). All three are implicitly at-release-time, but Invariants 1–2 are appropriate for pre-commit or CI, while Invariant 3 is heavyweight and belongs at release-tag time.
   - **Proposed change**: Add a gate-integration line to Candidate A's Mechanical verification section: "Invariants (1) and (2): fire as a CI lint step on every push to main (fast path; no runtime required). Invariant (3): fire at every release tag (heavyweight; requires runtime fixture). A release that has not passed all three verifiers is not a compliant release."
   - **Rationale**: Principle IX (Reproducibility) — identical inputs must produce identical outputs [`.orchestrator/memory/constitution.md`, Principle IX]. A verifier without a named gate point fires at no consistent point; "end-to-end install testing" becomes advisory rather than gated.
   - **Risk if ignored**: Invariant 3 degrades to "run it when you remember to." The principle's third invariant provides no structural release-time protection, and the first two verifiers run inconsistently depending on which team member initiates the release.

6. **Add violation remediation protocol to both candidates** (Priority: P2)
   - **Current state**: Neither candidate specifies what happens when a verifier reports FAIL — who remediates, in what timeframe, and how the remediation is recorded (inheritance-claims-blind.md, both Mechanical verification sections).
   - **Proposed change**: Add a remediation clause to both candidates: "A failing verifier result MUST be emitted as a structured FAIL event to the engine event log via `emit_event`. Remediation is required before the affected phase or release can be marked complete. Violations that cannot be remediated in the current release window are tracked in CONFORMANCE.md's Provisional remediation plan table with a named deadline not to exceed 30 days."
   - **Rationale**: Principle VI (State On Disk Is Truth) — "If it is not on disk, it did not happen. No exceptions." [`.orchestrator/memory/constitution.md`, Principle VI]. A violation acknowledged verbally and remediated without a disk-persisted record is invisible to the state machine, to crash recovery, and to future auditors. The CONFORMANCE.md Provisional remediation plan table is the established venue for this (CONFORMANCE.md, Provisional remediation plan section).
   - **Risk if ignored**: A verifier reports FAIL; the team acknowledges it in Slack; the release ships anyway. The mechanical enforcement chain breaks at the remediation step, making the principle advisory rather than gated.

7. **Specify dynamic installer enumeration for Candidate A's verifiers** (Priority: P2)
   - **Current state**: Candidate A's statement names three specific installer paths (`install-claude-code.sh`, `install-codex.sh`, `install-cursor.sh`, `install.sh`) and says the invariants apply to "any future runtime-adapter installer" (inheritance-claims-blind.md, Statement section for Candidate A). The verifiers as described would require manual updating when a new installer is added.
   - **Proposed change**: Add to Candidate A's Mechanical verification section: "Verifiers MUST enumerate `packaging/install/install-*.sh` dynamically. A new installer that appears in that directory is automatically in scope for all three invariants. A verifier that hardcodes installer paths does not satisfy Invariant (1)."
   - **Rationale**: Principle XI (Single Source of Truth) — the canonical record of which installers exist is the directory listing of `packaging/install/`, not a list hardcoded inside a verifier script [`.orchestrator/memory/constitution.md`, Principle XI]. Duplicating that list inside the verifier creates the exact synchronization hazard the principle is designed to prevent.
   - **Risk if ignored**: A fourth installer is added with a hardcoded version string. The verifier's hardcoded list does not include it. Invariant 1 reports PASS; the hardcoded string ships undetected.

8. **Resolve the Purpose-clause vs membership-gate ambiguity in the CONFORMANCE.md Independence Argument** (Priority: P2)
   - **Current state**: CONFORMANCE.md's Tier 2 Inheritance Basis argues that SOURCE B's three Purpose-clause prerequisites are "not load-bearing" for XXII and XII specifically (CONFORMANCE.md, Paragraph 2). This argument is structurally sound on the purpose-clause reading of the prerequisites but could be challenged on the membership-gate reading. The document disclaims the Relief pathway but does not resolve which reading applies.
   - **Proposed change**: Add a one-paragraph clarification to the Independence Argument: "The three SOURCE B Purpose-clause prerequisites are typed here as purpose-clause prerequisites — they describe the architectural context in which the Tier 2 suite constitution was authored, not universally-load-bearing membership-eligibility gates. Under the membership-gate typing, the Independence Argument would not be sufficient without a formal Relief invocation. The purpose-clause typing is adopted here because XXII and XII's normative bodies make no reference to deliberation substrates, plugin boundaries, or revenue models, which is the textual evidence that they were authored as domain-scoped principles rather than architecture-scoped principles."
   - **Rationale**: The criterion (i) check (inheritance-claims-blind.md, Evaluation directive) asks whether the membership basis preamble grants implicit relief without a formal Relief pathway. The answer depends on how the prerequisites are typed. Making the typing explicit forecloses re-litigation of this question at future amendments.
   - **Risk if ignored**: A future amendment or audit re-reads the prerequisites under the membership-gate interpretation, concludes the Independence Argument was implicit relief without formal routing, and initiates a re-ratification proceeding.

9. **Add grandfather protocol for pre-existing dead config knobs to Candidate B** (Priority: P3)
   - **Current state**: Candidate B declares a 0-dead baseline for this specific project but does not specify what happens when the principle is adopted by a project that starts with N dead knobs (inheritance-claims-blind.md, Mechanical verification section for Candidate B).
   - **Proposed change**: Add a grandfather clause: "Projects adopting this principle with a non-zero dead-knob baseline MUST document all existing dead knobs in CONFORMANCE.md's Provisional remediation plan table with a remediation deadline not to exceed 90 days from adoption date. A project in the grandfathering window is Provisional, not non-compliant."
   - **Rationale**: The CONFORMANCE.md Provisional remediation plan table is the established pattern for deadline-tracked open audits (CONFORMANCE.md, Provisional remediation plan section, rows for Principles II, VII, IX, XIV, XXVIII). A principle without a grandfathering protocol cannot be adopted by any project with pre-existing technical debt.
   - **Risk if ignored**: A downstream project adopts Candidate B and immediately fails compliance because of legacy dead knobs. The principle becomes a greenfield-only rule and is avoided by projects that most need it.
