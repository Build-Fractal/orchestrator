Single-commit authorship is the natural way to express that the three operations are jointly necessary and sufficient; it costs nothing additional and forecloses a class of future governance disputes the advocate has explicitly said should be foreclosed.

- **Dispute: Operational Definition Precision for "Fresh Project Fixture"**
  - **My claim**: The Invariant 3 operational definition of "fresh project fixture" should be "a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state." (Skeptic revision, Modified Recommendation 6.)

No script can mechanically determine what constitutes "minimum required by the runtime's project layout" for an arbitrary runtime — it requires a human to characterize what the runtime needs. This is the human-judgment gate Principle II prohibits for mechanical verification. The skeptic's formulation is objectively falsifiable: create an empty temporary directory, invoke the installer, record the resulting file system state. Those are the files. No interpretation is required. The gap between these definitions is not stylistic; it is a falsifiability gap that the entire motivation for Recommendation 6 exists to close.

If a runtime requires a scaffold, name it: "fresh project fixture for runtime R enumerates exactly [these files]." The base definition must be the most objective formulation; runtime-specific accommodations belong in declared preconditions, not in the core term.
  - **Proposed resolution path**: Adopt the skeptic's formulation as the base definition: "a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state." Add a runtime-specific escape hatch: "where a runtime requires pre-existing scaffold files before the installer can be invoked, those files MUST be enumerated explicitly in the smoke test fixture's documented preconditions and MUST NOT overlap with any file that the installation itself places." This preserves objective falsifiability for the default case and provides a declared, auditable escape hatch for the scaffold case rather than burying the accommodation in the base definition.

### Final Position Statement

**Non-Negotiables**

1. **VIII PATCH is a P1 pre-ratification prerequisite for Candidate B; it may not be deferred post-ratification.** The scope boundary between § VIII (file-system reachability of config files) and inherited Tier 2 XII (variable-level knob liveness within those files) is load-bearing for Candidate B's distinctness argument. That boundary must be constitutionally self-derivable from the constitution's plain text without requiring a reader to navigate CONFORMANCE.md's three-bucket table and deliberation artifacts in conjunction. Principle XI (Single Source of Truth) applies to governance documentation as much as to code: if the scope boundary lives only in CONFORMANCE.md and not in § VIII's text, the boundary has two candidate authoritative locations, and a reader applying the constitution's plain text alone can conclude § VIII already covers Candidate B's domain. The VIII PATCH is the minimum intervention that closes this ambiguity before Candidate B's scope boundary claim is load-bearing in a ratified principle.

2. **The follow-on amendment for Candidate A must resolve XI and X in a single commit; no partial state constitutes advancement-eligible evidence.** This is the mechanical enforcement of the conditional ratification's advancement gate. Principle II (Evidence Before Claims) requires that verification gates be checkable without human judgment. A gate that can be partially satisfied — the restructuring is committed, the X argument is committed, but the XI structural argument is absent — requires a human auditor to determine whether the partial state is sufficient. The single-commit constraint converts this from a judgment call into a file-presence check. The conditional ratification's purpose is to ensure that Candidate A's CONFORMANCE.md row cannot advance before the distinctness argument is structurally sound; that purpose is only realized if the gate is defined mechanically.

3. **The operational definition of "fresh project fixture" must be objectively falsifiable before it enters the follow-on amendment.** The definition must not require a human to determine what "minimum required by the runtime's project layout" means for an arbitrary runtime — that determination IS the judgment gate Principle II prohibits. The skeptic's formulation ("only the files the installer places there") is the correct base definition; runtime-specific scaffold requirements, if any, must be enumerated explicitly in named preconditions rather than folded into the base term. The goal of defining this term at all was to make `installer-smoke.sh` capable of deterministic PASS/FAIL; a base definition that reintroduces subjectivity defeats that goal.

**Flexibility**

1. **The exact wording of the single-commit enforcement clause in CONFORMANCE.md.** I am flexible on the precise formulation. What must be preserved: the entry must make explicit that Provisional status advancement is blocked until all three deliverables — restructuring, XI structural argument, X distinctness sentence — are present in the same amendment commit, and that no subset constitutes sufficient evidence. Any wording that makes this gate evaluable without human judgment satisfies the requirement.

I am flexible on the priority designation — either is post-ratification, and the urgency difference between P2 and P3 is negligible for a post-ratification task. This content forecloses re-litigation of the criterion (i) finding in future re-audits; the priority label does not affect that function.

What must be preserved: after the exclusion, the entire declared scope of Candidate B must be lintable by `check-dead-infra.sh`; no surface should remain in the normative body that the linter cannot reach; and the deferred clause must be recorded explicitly so future amendment authors know the scope boundary was intentionally drawn, not accidentally omitted.
