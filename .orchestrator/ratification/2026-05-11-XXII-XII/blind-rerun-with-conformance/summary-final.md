### Dangerous Contradictions Found

**Resolved Contradictions**

All six dangerous contradictions identified in Phase 2 were resolved through Phase 3 revisions. The resolutions are documented below in the order they appeared.

1. **Invariant 1 inclusion threshold: BLOCK vs. answerable challenge** (Advocate cross-review DC §1; Skeptic cross-review DC §1). The advocate initially recommended unconditional adoption of both candidates while acknowledging in its own Missed Opportunities section that the XI overlap was an unaddressed inclusion-criteria failure. The skeptic issued a pre-ratification BLOCK on Candidate A. These positions were logically contradictory: unconditional adoption cannot coexist with an acknowledged inclusion-criteria failure. Resolution: both agents converged on conditional ratification in Phase 3. The advocate conceded the contradiction in its own Phase 1 review and yielded on the BLOCK severity classification. The skeptic conceded that conditional ratification — Provisional status locked until the XI distinctness argument is authored as a follow-on amendment — is an acceptable ratification pathway. The advocate's Modified Rec 4 and the skeptic's Modified Rec 1 both adopt this framework.

2. **Mechanical verification criterion: capability demonstrated vs. algorithmic structure implied** (Advocate cross-review DC §2; Skeptic cross-review DC §2 framing). The advocate's Phase 1 framed the scripts' algorithmic structure as a valid feasibility argument satisfying the inclusion criterion at the feasibility level. The skeptic held that path-existence is "evidence of intent, not feasibility" and that the capability claim is overstated. Resolution: both agents converged on the skeptic's more operationally precise vocabulary. "Criterion 1 feasibility only; Criterion 3 enforcement deferred" becomes the canonical CONFORMANCE.md formulation. The advocate's Modified Rec 1 adopted the section rename ("Mechanical verification feasibility") as the structural fix; the skeptic's Surviving Rec 3 confirmed this as the correct remediation shape. Neither agent's position displaces the other — the rename addresses the heading; the PENDING notation addresses the evidence trail.

3. **VIII PATCH requirement for Candidate B: absent from advocate vs. P1 prerequisite from skeptic** (Skeptic cross-review DC §2). The advocate's Phase 1 characterization of Candidate B's scope boundary as "precisely articulated" was accurate as a description of CONFORMANCE.md's content but wrong as a claim about the constitution's self-sufficiency. Principle VIII's plain text — "every file, script, template, and configuration entry MUST be reachable from a live code path" — does not foreclose a reading that "configuration entry" encompasses individual config knobs. Resolution: the advocate explicitly yielded in Phase 3 ("The VIII PATCH error was a different kind of miss") and added the VIII PATCH as a New Recommendation at P1. The skeptic's Surviving Rec 4 was confirmed bilateral.

4. **Candidate A headline adoption recommendation: "adopt both" vs. multiple BLOCK-level gaps** (Skeptic cross-review DC §3). The advocate's unconditional adoption stance conflated adoption momentum with gap resolution. The skeptic identified this as placing Candidate A's CONFORMANCE.md row in the constitution with unresolved distinctness and falsifiability failures. Resolution: the advocate modified its headline recommendation to conditional ratification, conceding that "adoption cannot be unconditional — the Invariant 1 and X distinctness gaps are real inclusion-criteria failures, not just improvement opportunities." ### Systemic Contradictions

- **Ratification Timing as Default vs. Amendment Bundling as Default**
  - **Manifests in**: Advocate Dispute 1 (operational definitions pre-ratification vs. follow-on), Advocate Dispute 2 (restructure and X sentence pre-ratification vs. follow-on), Skeptic Dispute 1 (single-commit enforcement vs. sequential sub-steps for follow-on).
  - **Root cause**: The conditional ratification framework was designed to handle one class of gap (distinctness documentation requiring new analytical material). When applied to a second class of gap (undefined operational terms requiring only editorial text), the framework's bundling logic produces unnecessary delay. The spec does not distinguish between these two gap classes, leading both agents to apply the same mechanism to qualitatively different problems.
  - **Implication for spec**: The conditional ratification framework should specify two tracks: Track A (editorial/definitional gaps whose content is agreed) must be authored before the principle enters the constitution, because they address inclusion criterion failures; Track B (analytical/structural gaps requiring new material) may be deferred to a follow-on amendment under the Provisional-cap mechanism. This distinction eliminates ambiguity about which gaps must be pre-ratification without requiring all agreed editorial content to wait for new analytical work.

- **Constitution Plain-Text Self-Sufficiency vs. CONFORMANCE.md Delegation**
  - **Manifests in**: S4/A-N (VIII PATCH requirement), S9 (deliberation path anchor), A8/S-N (purpose-clause typing clarification), Skeptic Dispute 1 (discoverability of "next MAJOR" trigger condition from SOURCE B L1181).
  - **Root cause**: The project uses CONFORMANCE.md as an extended governance layer that records scope boundaries, inheritance bases, and verification evidence. But the constitution's principles are enforced by readers who may apply plain text alone. When CONFORMANCE.md carries load-bearing scope boundaries not derivable from the constitution's text, the system has two authoritative sources that can diverge — the exact problem Principle XI exists to prevent.
  - **Implication for spec**: Any scope boundary that is load-bearing for a principle's distinctness argument must be derivable from the constitution's own text without cross-referencing CONFORMANCE.md. CONFORMANCE.md should elaborate and evidence scope boundaries that are already stated in the constitution; it should not be the sole authoritative source of those boundaries. The VIII PATCH models this correctly: CONFORMANCE.md records the evidence; the constitution's text states the boundary.

- **Feasibility Claims vs. Capability Demonstration in Mechanical Verification**
  - **Manifests in**: S3 (section rename from "Mechanical verification" to "Mechanical verification feasibility"), A1 (PENDING status notation), S6 (priority upgrade for operational definitions), S8 (Criterion 1/3 labels in CONFORMANCE.md), Skeptic Dispute 2 (definition precision for "fresh project fixture").
  - **Root cause**: Candidate A presents three path-existence stubs under a "Mechanical verification" heading that implies the verification has been partially performed. The term "feasibility" is used loosely — the advocate initially treated the scripts' algorithmic structure as constituting feasibility, while the skeptic held that only a running script constitutes feasibility evidence. The spec does not define what level of implementation satisfies the inclusion criterion for mechanical verification capability.
  - **Implication for spec**: The inclusion criteria should define a minimum bar for mechanical verification capability: a named script with a documented algorithm, at a stable path, that emits PASS/FAIL based on codebase state (not on its own path existence). Stubs satisfy the "named path" requirement but not the "emits PASS/FAIL based on codebase state" requirement. Separating these into Criterion 1 (design feasibility) and Criterion 3 (enforcement capability), as both agents converged on using, should be adopted as standard vocabulary in the governance framework.

- **Scope Declaration Outrunning Enforcement Infrastructure**
  - **Manifests in**: A3/S7 (PENDING frontmatter clause in Candidate B), A2/S6 (undefined terms in Invariant 3 preventing enforcement), A1 (stubs lacking enforcement capability for Candidate A invariants).
  - **Root cause**: Both candidates declare scope and enforcement commitments that their current infrastructure cannot satisfy. Candidate A declares three invariants with stubs; Candidate B declares four surface types with one PENDING. In both cases, the principle's declared scope exceeds its verifiable scope at the time of ratification. The spec's inclusion criteria require mechanical verification capability but do not specify the scope of that capability must exactly match the principle's declared scope.
  - **Implication for spec**: The inclusion criteria should explicitly require that the principle's declared scope and its verified scope be coextensive at ratification. Any scope surface that cannot yet be linted or enforced mechanically must either be excluded from the principle's normative body or explicitly bracketed as "deferred extension pending [named precondition]." CONFORMANCE.md's clause-mapping scaffold already models this pattern with PENDING cells; the spec should formalize it as a ratification gate.

- **Enabling-Constraint vs. Independent-Invariant Architecture for Multi-Invariant Principles**
  - **Manifests in**: S5 (restructure Candidate A to lead with Invariant 3), S1/A4 (distinctness burden shifts when Invariants 1–2 are enabling constraints vs. independent invariants), Skeptic Dispute 1 (whether Invariants 1–2 in follow-on restructure must be single-commit with XI argument).
  - **Root cause**: Candidate A presents three invariants as independent constituents of equal weight, each carrying its own distinctness burden. Invariants 1 and 2 have thin distinctness arguments from Principles XI and X respectively; Invariant 3 has no clear analog. When all three are presented as independent invariants, the inclusion case rests on the two weakest arguments. The enabling-constraint reframing (Invariant 3 is the principle's novel claim; Invariants 1–2 are completeness constraints that make Invariant 3 testable) changes the distinctness analysis structurally: under this framing, Invariants 1–2 do not need independent distinctness standing, only coherent functional relationship to Invariant 3.
  - **Implication for spec**: Multi-invariant principles should distinguish their primary governance claim (the novel concern that the principle addresses) from enabling constraints (secondary invariants that make the primary testable). This distinction should be explicit in the principle's structure, not implicit in the presentation order. The enabling-constraint status should appear in the principle text, not only in the deliberation record.

- **Dispute: Timing of Operational Definitions for Invariant 3**
  - **Positions**: Advocate (Surviving Rec 2 and Dispute 1, Phase 4): operational definitions — "fresh project fixture" and "works" — must be added to Candidate A's Invariant 3 text before the principle enters the constitution. Skeptic (Modified Rec 6 and Dispute 2, Phase 4): definitions should be in the follow-on amendment bundled with the XI and X gaps.
  - **Arguments**: The advocate argues that undefined operational terms in a principle's normative clause constitute a falsifiable-scope inclusion criterion failure — not a distinctness documentation gap — and that conditional ratification (Provisional status) is the wrong mechanism for this class of failure. The principle's text, as submitted for ratification, must be mechanically falsifiable, and "works" is not a falsifiable term. Adding two definition sentences is an editorial change of agreed content that resolves an inclusion criterion failure at zero cost; deferring it means the constitution contains a principle that fails the inclusion criteria it was evaluated against. The skeptic argues that the two definitions should be bundled with the XI and X gaps in the follow-on amendment for single-commit atomicity — neither gap can be independently closed without the other — and that the Provisional-cap mechanism enforces the requirement that all conditions be satisfied before status advancement.
  - **Synthesizer assessment**: The advocate's position is analytically stronger. The two gap classes are genuinely distinct. Distinctness documentation gaps (XI structural argument, X distinctness sentence) require new analytical material to be authored — they are deferred because the work is substantive. Definitional gaps (undefined "works," undefined "fresh project fixture") require two sentences of editorial text whose content is already agreed between both agents. Deferring agreed editorial text to wait for complex analytical work is procedurally suboptimal and architecturally unsound: it produces a gap state in which the constitution contains a principle whose normative clause fails the falsifiable-scope inclusion criterion on its face. The Provisional-cap mechanism was designed for distinctness documentation gaps, not for principle text that cannot be mechanically applied as written. The skeptic's bundling rationale ("neither gap can be independently closed without the other") addresses the XI and X gaps, not definitional gaps — there is no coherent reason why the definition of "fresh project fixture" depends on the XI structural argument being authored in the same commit.
  - **Recommended resolution**: Adopt the advocate's position. Author the operational definitions as a pre-ratification text amendment to Candidate A's Invariant 3. The CONFORMANCE.md Provisional-cap entry is written to reflect that the definitions are already present and that the remaining conditions for advancement are: (a) the Invariant 3-leads restructuring with enabling-constraint framing; (b) the XI structural distinctness argument taking one of three named paths; and (c) the X distinctness sentence within the restructured form. See the wording dispute below (Dispute: Definition Precision for "Fresh Project Fixture") for the exact formulation to adopt.

The advocate is correct that the Provisional-cap mechanism can enforce bundled advancement conditions regardless of commit timing, and that deferring agreed editorial text creates unnecessary delay. The skeptic is correct that a single-commit requirement provides a simpler mechanical enforcement mechanism. However, the advocate's key insight — that the cap text's comprehensiveness, not the commit structure, is the operative enforcement — is architecturally sound. A CONFORMANCE.md cap entry that explicitly lists "restructuring with enabling-constraint framing" as a condition for advancement is equally mechanical whether the restructuring was authored pre-ratification or in the follow-on. The advocate's flexibility concession is decisive: "If the synthesizer prefers the skeptic's bundled follow-on approach, the minimum condition is that the Provisional-cap text explicitly covers both the restructure and the X sentence — not only the XI structural argument — so the cap is comprehensive regardless of which commits they arrive in." The restructure and X sentence MAY be authored pre-ratification as editorial changes — their content is agreed and they improve the candidate text immediately. If they are authored pre-ratification, the CONFORMANCE.md Provisional-cap entry reflects this and lists only the XI structural argument as the remaining condition for advancement. If they are NOT authored pre-ratification, the CONFORMANCE.md Provisional-cap entry explicitly lists all three conditions (restructuring, XI structural argument, X sentence) and requires them to be present in the follow-on amendment. The cap's comprehensiveness — not the commit structure — is the operative enforcement mechanism. - **Dispute: Definition Precision for "Fresh Project Fixture"**
  - **Positions**: Advocate (Surviving Rec 2, Phase 3 Revision): "a temporary directory containing only the minimum files required by the runtime's project layout, with no pre-existing `.orchestrator/` directory." Skeptic (Dispute 2, Phase 4): "a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state" — base definition — plus an explicit escape hatch: "where a runtime requires pre-existing scaffold files before the installer can be invoked, those files MUST be enumerated explicitly in the smoke test fixture's documented preconditions and MUST NOT overlap with any file that the installation itself places."
  - **Arguments**: The advocate's formulation accommodates runtimes that require a scaffold file before an installer can be invoked, encoding this flexibility into the base definition via "minimum files required by the runtime's project layout." The skeptic holds that "minimum files required by the runtime's project layout" introduces a judgment-dependent term: no script can mechanically determine what constitutes "minimum required by the runtime's project layout" for an arbitrary runtime. This is precisely the human-judgment gate Principle II prohibits for mechanical verification. The skeptic's formulation is objectively falsifiable: create an empty temporary directory, invoke the installer, record the resulting file system state — those are the files. Runtime-specific scaffold requirements, if any, must be enumerated explicitly as named preconditions, not embedded in the base definition.
  - **Synthesizer assessment**: The skeptic's position is analytically stronger and should be adopted. The purpose of defining "fresh project fixture" is to make `installer-smoke.sh` capable of deterministic PASS/FAIL without human judgment. The advocate's formulation imports the exact judgment it was designed to eliminate: "minimum files required by the runtime's project layout" requires a human — or a runtime-specific knowledge base — to determine what counts as minimum and what counts as required. The skeptic's base definition ("only the files the installer places there") is mechanically deterministic: run the installer, observe the file system diff. The escape hatch mechanism the skeptic proposes is the architecturally correct response to the scaffold edge case: make the accommodation explicit and auditable, not implicit in the base definition. An explicit named precondition is more enforceable than a definition that silently accommodates variation.
  - **Recommended resolution**: Adopt the skeptic's two-part resolution. Base definition: "A fresh project fixture is a temporary directory containing only the files the installer places there, with no prior `.orchestrator/` state. The fixture is created immediately before and destroyed immediately after each release gate run." Escape hatch: "Where a runtime requires pre-existing scaffold files before the installer can be invoked, those files MUST be enumerated explicitly in the smoke test fixture's documented preconditions and MUST NOT overlap with any file that the installation itself places. A fixture specification that requires runtime-specific preconditions must document those preconditions in a named fixture manifest file within `scripts/verify/`."
