**Input**: User description: "M032 Wiki Distribution and Init Integration: make orchestrator:init produce a working, reviewable, comment-enabled mkdocs Material wiki for any new orchestrator-managed project. Replaces ad-hoc 1,157-file project-asset bulk-copy in install-claude-code.sh with a managed packaging/bundle/manifest.yml project_assets schema (copy + symlink modes); ships orchestrator:wiki-init command (default + --with-giscus + --deploy scopes); parameterizes wiki/mkdocs.yml + Giscus partial per-project; adds Python toolchain probe; introduces --with-<feature> progressive-opt-in flag pattern on init; adds glossary surface (wiki/glossary.md) load-bearing for M033 grilling protocol; addresses 11 root-cause findings A-K from 2026-04-28 pbj-central-mono-repo bootstrap. ## Problem Statement

The orchestrator's wiki tooling — mkdocs Material config, Giscus comment partial, Python deps, scan/generate/deploy helpers, and Giscus-IDs-from-GH automation — was built in M012 to render *this* repo's `.orchestrator/` tree for *this* repo's team. The 2026-04-28 `pbj-central-mono-repo` bootstrap session proved it does not cross the install boundary: a fresh `orchestrator:init` produces 1,157 framework files in the consumer project (via an unmanaged hardcoded bulk-copy in `packaging/install/install-claude-code.sh:287-330` that bypasses `packaging/bundle/manifest.yml` entirely) but ships zero wiki tooling. The consumer must hand-stitch across `wiki/`, `scripts/wiki/`, `scripts/diagnostics/wiki-giscus-*.sh`, `mkdocs.yml`, and theme overrides — and even then ends up with the orchestrator repo's branding, Giscus wired to the *orchestrator's* discussions, no GH Pages deploy, and no Python probe.

Three concrete pain-points follow. First, **distribution surface is unmanaged**: the bulk-copy step is the second instance of project-asset distribution (M012's wiki tooling was the first), neither went through the bundle manifest, and there is no schema, no per-asset mode, no opt-in/opt-out, and no symlink option. Consumer projects accumulate framework files in their git history or maintain a defensive `.gitignore` workaround. Second, **mkdocs.yml + Giscus partial + nav generator hard-code per-project values**: site identity, repo URLs, Giscus IDs, and nav entries are all this-repo-specific, so a copy-as-is install produces a wiki that looks and behaves wrong. Third, **`init` has no flag-progressive opt-in pattern and no remote-state mutation surface**: enabling Discussions, deploying to GH Pages, and toggling Pages-from-`gh-pages` are four manual GitHub steps after `init`, defeating the team-onboarding goal.

The minimum surface that fixes all three is: (a) a `project_assets:` schema in `packaging/bundle/manifest.yml` with `mode: copy|symlink` per entry that subsumes the existing hardcoded `RUNTIME_DIRS` bulk-copy and adds the wiki tooling; (b) an `orchestrator:wiki-init` command with three composable scopes (default copy+template, `--with-giscus`, `--deploy`); (c) `orchestrator:init --with-wiki [--with-giscus] [--deploy]` pass-through with a Python toolchain probe; (d) parameterized `mkdocs.yml`, parameterized Giscus partial, and a custom-nav region in `wiki-generate-nav.sh` so operator additions survive regenerate; (e) a project-glossary surface (`wiki/glossary.md`) load-bearing for M033's grilling protocol.

This feature explicitly does not re-litigate mkdocs Material as the static-site generator (M012 commitment), add a wiki-content-authoring command (authoring lives in `orchestrator:specify` / `orchestrator:plan-phase` / etc.), introduce search backends beyond mkdocs built-in, support custom domains beyond GH Pages defaults, ship Vercel/Netlify/Cloudflare adapters, add wiki-side comment moderation (Giscus delegates to GitHub Discussions natively), or add multi-language i18n.

## User Scenarios & Testing *(mandatory)*

### Minimal Slice (Phase 1 Load-Bearing Scope)

The smallest coherent subset of user stories that closes the dogfood loop is **US-1 + US-2**: managed `project_assets:` schema replaces the hardcoded `RUNTIME_DIRS` bulk-copy (US-1), and `orchestrator:wiki-init` ships wiki tooling into a fresh fixture project that can serve locally (US-2). With these two stories shipped, every consumer project can opt into a working local wiki without hand-stitching. Subsequent stories (`--with-giscus`, `--with-wiki --deploy` end-to-end, custom-nav preservation, glossary surface) are defended on top of this slice — each one is independently shippable but assumes the slice exists.

### User Story 1 — Managed project-asset distribution replaces unmanaged bulk-copy (Priority: P1)

An operator running `orchestrator:init` against a fresh project today gets 1,157 framework files copied into `<project>/{commands,scripts,references,templates}/` via an unmanaged hardcoded loop in `install-claude-code.sh:287-330` that bypasses the bundle manifest entirely. The operator wants the same files to land — but declared in `packaging/bundle/manifest.yml` under a `project_assets:` schema with explicit `source:`, `target:`, and `mode: copy|symlink` per entry — so future additions (wiki tooling, GitHub Actions workflows, project-local hooks) flow through one schema, and consumers can choose `mode: symlink` (resolved against `~/.claude/orchestrator-runtime/<version>/` or equivalent) to keep their git history clean of framework copies.

**Why this priority**: P1 because every other story in this spec (wiki-init, --with-giscus, --deploy, glossary) consumes the `project_assets:` surface. Without US-1, US-2..US-N each have to invent their own ad-hoc distribution path — exactly the failure mode that produced today's two parallel codepaths (manifest-aware skills/hooks + manifest-bypassing project bulk-copy). US-1 is also the mechanical migration: the four hardcoded `RUNTIME_DIRS` become four `project_assets:` entries, behavior is byte-identical at `mode: copy`, and the migration cost is paid once.

**Independent Test**: `tests/m032-acceptance/p01-managed-bundle-shape.sh` against `tests/fixtures/m032-fresh-project-fixture/`: run `bash packaging/install/install-claude-code.sh --project-dir <fixture>` once → assert all four runtime dirs (`commands/`, `scripts/`, `references/`, `templates/`) present at expected paths with file counts matching today's behavior; run a second time → assert byte-identical output (idempotency, M025 pinned-sha gate extension); inspect `<fixture>/.orchestrator/installed-files.txt` → assert per-asset `mode:` field present for every entry.

**Acceptance Scenarios**:

1. **Given** a fresh fixture project with no `<fixture>/{commands,scripts,references,templates}/` directories, **When** the operator runs `bash packaging/install/install-claude-code.sh --project-dir <fixture>`, **Then** all four directories are populated, file counts match the pre-M032 behavior, `<fixture>/.orchestrator/installed-files.txt` exists, and every line in the manifest carries a `mode:` field (`copy` for v1 default).
2. **Given** an already-installed fixture project, **When** the operator re-runs the installer, **Then** the second run is byte-identical to the first (idempotent) and `installed-files.txt` is unchanged.
3. **Given** a `project_assets:` entry declared `mode: symlink`, **When** the installer runs on a POSIX host with `~/.claude/orchestrator-runtime/<version>/` populated, **Then** the consumer-side path is a symlink resolving to the runtime cache and the consumer's git history sees zero framework files.
4. **Given** a `project_assets:` entry declared `mode: symlink` on a Windows host without symlink privilege, **When** the installer runs, **Then** the installer fails closed with a clear diagnostic pointing at "POSIX-only in v1" and exits non-zero (no silent fallback).

### User Story 2 — `orchestrator:wiki-init` ships a working local wiki to a fresh project (Priority: P1)

An operator on a fresh project who wants a team-onboarding wiki today must hand-copy `wiki/mkdocs.yml`, `wiki/overrides/`, `wiki/requirements.txt`, six `scripts/wiki/*.sh` helpers, four `scripts/diagnostics/wiki-giscus-*.sh` helpers, and the `scripts/diagnostics/giscus-ids-from-gh.sh` automation — and then sed-edit `mkdocs.yml` for site identity, sed-edit the Giscus partial for IDs, and `pip install -r wiki/requirements.txt`. The operator wants `bash scripts/lifecycle/wiki-init.sh --project-dir <fixture>` to: (a) read the wiki tooling from the `project_assets:` entries shipped by US-1, (b) sed-substitute `{{site_name}}`, `{{site_description}}`, `{{site_url}}`, `{{repo_url}}` in the copied `mkdocs.yml` from the project's git remote (with `--site-name`, `--site-description` overrides), (c) leave the Giscus partial in placeholder state (filled by `--with-giscus` in US-3), (d) probe for `python3` + `pip3` and print actionable platform-specific diagnostics if missing, and (e) leave the wiki ready for `bash <fixture>/scripts/wiki/wiki-serve.sh` to succeed at `:8000`.

**Why this priority**: P1 because the local-serve flow is the operator's first sanity check that the wiki tooling actually works in the consumer's project before any remote-state mutation (Discussions, Pages). Without US-2, US-3 (`--with-giscus`) and US-4 (`--deploy`) have no foundation — they extend US-2's scope, they don't replace it. US-2 is also the smallest surface that closes the team-onboarding dogfood loop: an operator can run `wiki-init`, serve locally, share the local URL with the team, and gather feedback before committing to a deploy.

**Independent Test**: `tests/m032-acceptance/p02-wiki-init-default-scope.sh` against `tests/fixtures/m032-fresh-project-fixture/`: pre-condition fixture has `python3` available (skip with `SKIP_REASON` if not); run `bash scripts/lifecycle/wiki-init.sh --project-dir <fixture>` → assert `<fixture>/wiki/mkdocs.yml` exists and `site_name:` / `site_url:` / `repo_url:` fields are *not* the orchestrator's values (sed-substitution fired); start `wiki-serve.sh` in background → assert `curl -fsS http://localhost:8000 | grep -q "<title>"` succeeds; teardown.

**Acceptance Scenarios**:

1. **Given** a fresh fixture project with US-1's bundle install completed and a git remote pointing at `<owner>/<repo>`, **When** the operator runs `bash scripts/lifecycle/wiki-init.sh --project-dir <fixture>`, **Then** `<fixture>/wiki/mkdocs.yml` is copied from the bundle, the four templated fields resolve from the git remote (`site_url=https://<owner>.github.io/<repo>/`, `repo_url=https://github.com/<owner>/<repo>`, `site_name=<repo>` default), and the Giscus partial under `<fixture>/wiki/overrides/` retains placeholder tokens.
2. **Given** the operator passes `--site-name "PBJ Central"` and `--site-description "Provider mono-repo wiki"`, **When** `wiki-init` runs, **Then** those values override the defaults in the rendered `mkdocs.yml`.
3. **Given** `python3` is missing from `PATH`, **When** `wiki-init` probes the toolchain, **Then** the command exits non-zero with a platform-aware diagnostic (`brew install python3` on darwin, `apt install python3` on linux) and writes nothing to disk.
4. **Given** US-1's bundle install + US-2's `wiki-init` have completed, **When** the operator runs `bash <fixture>/scripts/wiki/wiki-serve.sh`, **Then** mkdocs serves at `:8000` and an HTTP `GET /` returns a valid HTML page rendering the project's `.orchestrator/**.md` content.
5. **Given** an already-`wiki-init`'d project, **When** the operator re-runs `wiki-init` without `--force`, **Then** the command preserves any operator edits to the templated files and exits 0 with a "no changes" diagnostic (idempotency).

### User Story 3 — `--with-giscus` wires comments to the consumer's own discussions (Priority: P2)

The operator wants Giscus comments wired against *the consumer project's* GitHub Discussions, not the orchestrator's. Today, even after a successful `wiki-init`, the Giscus partial under `<fixture>/wiki/overrides/` carries the orchestrator's hardcoded `data-repo`, `data-repo-id`, `data-category`, `data-category-id` — silently routing team review noise to the wrong place. The operator wants `bash scripts/lifecycle/wiki-init.sh --with-giscus --repo <owner>/<repo> --category "Wiki Comments"` to invoke `scripts/diagnostics/giscus-ids-from-gh.sh`, parse the four `export GISCUS_*` lines from its stdout, sed-substitute `{{giscus_repo}}` / `{{giscus_repo_id}}` / `{{giscus_category}}` / `{{giscus_category_id}}` into the partial, and run `scripts/diagnostics/wiki-giscus-config-check.sh` as a post-step verifier.

**Why this priority**: P2 because Giscus comments are a substantial onboarding win but not load-bearing for the local-serve dogfood loop. US-2 closes the local loop without Giscus; US-3 is the second composable scope that turns the local wiki into a team-collaboration surface. P2 reflects that some consumer projects (private internal repos without team collaboration needs) may never enable comments.

**Independent Test**: `tests/m032-acceptance/p02-wiki-init-with-giscus.sh` against `tests/fixtures/m032-fresh-project-fixture/`: pre-condition: US-2 already ran; mock `giscus-ids-from-gh.sh` to emit deterministic fixture IDs (avoid GraphQL rate-limit dependence in CI); run `bash scripts/lifecycle/wiki-init.sh --with-giscus --repo fixture-owner/fixture-repo --category "Wiki Comments" --project-dir <fixture>` → assert the partial under `<fixture>/wiki/overrides/` carries the four fixture IDs (no orchestrator values remain); run `bash scripts/diagnostics/wiki-giscus-config-check.sh --project-dir <fixture>` → assert exit 0.

**Acceptance Scenarios**:

1. **Given** a US-2-completed fixture and valid `--repo`/`--category` flags, **When** the operator runs `wiki-init --with-giscus`, **Then** the four `data-*` attributes in the rendered Giscus partial match the values produced by `giscus-ids-from-gh.sh` for the supplied repo/category.
2. **Given** an invalid `--repo` flag (repo does not exist or `gh` lacks access), **When** `--with-giscus` runs, **Then** `giscus-ids-from-gh.sh` fails fast, the partial is left in placeholder state (no partial sed-substitution), and the command exits non-zero with `integration-giscus-config-failed: <reason>`.
3. **Given** a previously-configured Giscus partial on the consumer side, **When** `wiki-init --with-giscus` re-runs with different `--repo`/`--category` flags, **Then** the partial is re-substituted with the new IDs (overwrite is the documented re-run behavior; reversibility is "re-run with corrected flags").
4. **Given** `--with-giscus --category "Nonexistent Category"`, **When** `giscus-ids-from-gh.sh` fails to resolve the category, **Then** the command exits non-zero with a clear diagnostic — category creation is out of scope for v1 (delegated to operator, requires GH Discussions admin scope).

### User Story 4 — `--deploy` produces a live wiki URL with one command (Priority: P2)

The operator wants `bash scripts/lifecycle/wiki-init.sh --with-wiki --with-giscus --deploy --project-dir <fixture>` to execute, in order: (a) `gh api --method PATCH /repos/<owner>/<repo>` with `has_discussions=true` (idempotent), (b) `bash <fixture>/scripts/wiki/wiki-deploy.sh` for the first GH Pages push (wiki-deploy.sh, not direct `mkdocs gh-deploy`, with the cwd vs `repo_url:` sanity gate from Finding J), (c) `gh api --method PUT /repos/<owner>/<repo>/pages` with `source: { branch: gh-pages, path: / }`, and (d) print the live URL to stdout. After the command completes, an HTTP `GET` against the printed URL returns 200 with a rendered nav and the Giscus iframe loads without JS console errors.

**Why this priority**: P2 because `--deploy` mutates remote state (Discussions, Pages, branches) and is correctly out of scope for many internal-only or local-development projects. US-4 is the third composable scope that turns the team-collaboration wiki into a publicly-shared (or org-shared) artifact. P2 also reflects that `--deploy` carries the highest reversibility cost (delete `gh-pages` branch + DELETE `/pages` + flip Discussions off) and the highest blast-radius (Finding J's silent cross-project force-push class of bug).

**Independent Test**: `tests/m032-acceptance/p03-wiki-init-deploy-live.sh` against a throwaway GH repo (created via `gh repo create <ts>-m032-fixture --private`, deleted in teardown): run `bash scripts/lifecycle/wiki-init.sh --with-wiki --with-giscus --deploy --project-dir <fixture> --repo <ts>-m032-fixture`; assert printed URL responds 200 within `M032_DEPLOY_PROPAGATION_TIMEOUT` seconds (default 90s, GH Pages can take ~60s to propagate); assert the served HTML contains the Giscus partial's per-fixture `data-repo` attribute (proves the partial templating loop closed end-to-end); teardown via `gh repo delete <ts>-m032-fixture --yes` and verify no orphan state in this repo (no leaked branches, no leaked `.orchestrator/` files).

**Acceptance Scenarios**:

1. **Given** a throwaway GH repo with no Discussions, no Pages, and no `gh-pages` branch, **When** the operator runs the full `--with-wiki --with-giscus --deploy` command, **Then** Discussions become enabled, the `gh-pages` branch is created, Pages source is set to `gh-pages` root, the live URL is printed to stdout, and an HTTP `GET` against the URL returns 200.
2. **Given** the operator is in `<project-B>/` cwd but invokes `wiki-init --deploy --project-dir <project-A>`, **When** `wiki-deploy.sh` runs its sanity gate, **Then** the gate compares `repo_url:` parsed from `<project-A>/wiki/mkdocs.yml` against `git -C $cwd remote get-url origin`, detects the mismatch, and exits non-zero with a clear cross-project hazard diagnostic (Finding J counter-pattern).
3. **Given** a previously-deployed wiki, **When** `--deploy` re-runs, **Then** the `gh api` calls are idempotent (Discussions already on → no-op; Pages already configured **with compatible source (`gh-pages` root)** → no-op; **Pages configured with incompatible source (e.g., `docs/` on `main`) → abort with diagnostic unless `--force-pages-reconfigure` is passed**, per MIT-007), `wiki-deploy.sh` updates the `gh-pages` branch, and the live URL is reprinted.
4. **Given** `--deploy` succeeds, **When** the operator runs the documented teardown (`gh repo delete <fixture-name> --yes`), **Then** no artifacts remain in the orchestrator repo and no orphan state remains in `<fixture>/.orchestrator/`.

### User Story 5 — Custom-nav region preserves operator additions across regenerate (Priority: P2)

The operator wants to add project-specific top-level nav entries (Spec, Domain Decisions, project-specific landing pages) to the consumer wiki's `mkdocs.yml`, and have those entries survive every subsequent run of `wiki-generate-nav.sh`. Today, `wiki-generate-nav.sh` rewrites the entire `nav:` block between `# >>> M012-P01 nav` and `# <<< M012-P01 nav end` markers, silently destroying any operator additions. The operator wants the nav block split into two regions: `# >>> auto-nav` ... `# <<< auto-nav end` (managed wholly by the generator: Constitution, Decisions, Knowledge, Milestones, Proposals, Glossary) and `# >>> custom-nav` ... `# <<< custom-nav end` (preserved verbatim across regenerates).

**Finding H (nav-workaround durability)** *(inline characterization per MIT-009)*: During the 2026-04-28 PBJ pilot bootstrap, operators hand-authored `include` stubs in `mkdocs.yml`'s nav block to compensate for the nav generator silently overwriting custom entries. The stubs were discarded on every subsequent `wiki-generate-nav.sh` run, requiring re-authoring. US-5 addresses this by introducing a custom-nav region preserved verbatim across regenerates — the operator's workaround becomes durable rather than throwaway. US-5 AS-4 (MIT-005) extends this to non-empty content already present between legacy `# >>> M012-P01 nav` markers, so first-regenerate migration moves those entries into the new custom-nav region rather than discarding them.

**Why this priority**: P2 because Finding I's data is empirical (today's PBJ workaround for Finding H is throwaway after first regenerate), and US-5 unblocks the "hand-author include stubs" workaround that lets operators address Finding H consumer-side without waiting for Finding H's full scanner extension to land in M032. P2 also reflects that operators on day-one have no nav customizations — US-5 is load-bearing on day-N.

**Independent Test**: `tests/m032-acceptance/p02-wiki-generate-nav-custom-region.sh` against the orchestrator's own `wiki/mkdocs.yml`: pre-condition: write a known custom-nav block between the new markers; run `bash scripts/wiki/wiki-generate-nav.sh --root .` → assert the custom-nav region is byte-preserved verbatim; assert the auto-nav region was regenerated.

**Acceptance Scenarios**:

1. **Given** an `mkdocs.yml` with both `auto-nav` and `custom-nav` regions populated, **When** the operator runs `wiki-generate-nav.sh`, **Then** the auto-nav region is rewritten and the custom-nav region is byte-identical.
2. **Given** an `mkdocs.yml` migrating from the legacy `# >>> M012-P01 nav` markers WITH **empty** content between the markers, **When** `wiki-generate-nav.sh` runs the first time, **Then** the legacy markers are migrated to `# >>> auto-nav` markers in-place, an empty `# >>> custom-nav` region is appended, and the rendered nav matches the legacy output (zero behavior change at empty-custom).
3. **Given** the operator removes the `custom-nav` markers entirely (manual edit), **When** `wiki-generate-nav.sh` runs, **Then** the generator re-creates an empty `custom-nav` region (self-healing).
4. *(MIT-005)* **Given** an `mkdocs.yml` migrating from legacy `# >>> M012-P01 nav` markers WITH **non-empty** content between the markers (operator hand-added entries — the named PBJ pilot population), **When** `wiki-generate-nav.sh` runs the first time, **Then** the non-empty legacy content is moved verbatim into the new `# >>> custom-nav` region (NOT discarded), and a migration diagnostic is emitted to stdout listing which nav entries were preserved (e.g., `Migrated N custom nav entries from legacy markers to custom-nav region`).

### User Story 6 — `wiki/glossary.md` ships as a first-class wiki artifact load-bearing for M033 (Priority: P2)

The operator wants `wiki/glossary.md` to exist as a project-glossary path convention — alphabetized term entries with one-line definitions and at most a two-line elaboration — that (a) `wiki-scan-sources.sh` includes (default-on, prepended as the second top-level entry after Constitution), (b) a thin `scripts/knowledge/lookup-mems.sh --kind=glossary` adapter reads to synthesize records for `build-context.sh` to inject into Standard/Full payloads, and (c) M033's grilling protocol writes into inline as terms resolve. The glossary is *project-shaped* (one per project, single file, owned by the operator, distributed via the wiki) — distinct from M020's content-shaped knowledge kinds (`pattern | convention | lesson | decision`).

**Why this priority**: P2 because the glossary surface is **load-bearing for M033's grilling protocol** (M033 P01–P02 commit to "update doc inline as terms resolve" — the doc must exist before the protocol runs). Without US-6, M033 either fails to land its grilling-loop discipline or invents an ad-hoc glossary path, fragmenting the project-glossary surface. US-6 is also small enough to ride P01 alongside the bundle work or P02 alongside `wiki-init` — phase placement is a #Q-4 question — but the *interface* (path, wiki rendering, knowledge-graph adapter) is the spec contract M033 plans against.

**Independent Test**: `tests/m032-acceptance/p0X-glossary-surface.sh` against the orchestrator's own repo: pre-condition: write a sample `wiki/glossary.md` with three test entries; run `bash scripts/wiki/wiki-scan-sources.sh --root . --include-glossary` → assert glossary path appears in the source list; run `bash scripts/knowledge/lookup-mems.sh --kind=glossary` → assert the three entries appear as records with stable IDs; run `bash scripts/wiki/wiki-generate-nav.sh --root .` → assert glossary is the second nav entry (after Constitution).

**Acceptance Scenarios**:

1. **Given** `wiki/glossary.md` exists with N alphabetized entries, **When** `wiki-scan-sources.sh --include-glossary` runs, **Then** the glossary path is enumerated and `wiki-generate-nav.sh` places it as the second top-level nav entry under "Glossary".
2. **Given** `wiki/glossary.md` is absent, **When** the same scanner+generator pair runs, **Then** the auto-nav region renders without a Glossary section (no broken link, no warning beyond a debug-level diagnostic).
3. **Given** a glossary with three entries, **When** `lookup-mems.sh --kind=glossary` runs, **Then** the three entries are synthesized as records with stable IDs derivable from the term name (so cross-references compound across regenerates).
4. **Given** a Quick-profile `build-context.sh` invocation for a task that touches one glossary term, **When** the glossary adapter runs under the Quick traversal contract, **Then** only the touched term is injected (not the full glossary), preserving the M031 Quick-profile budget.

### User Story 7 — Scanner enumerates `proposals/`, `wiki.extra_dirs:`, and flat-knowledge entries (Priority: P3)

The operator wants `wiki-scan-sources.sh` extended with three additive enumerations: (a) `.orchestrator/proposals/*.md` rendered under a top-level nav section (name TBD, see #Q-5) with a per-entry stage badge (`stub | brief | specified | active | closed`) read from frontmatter; (b) `<project>/.orchestrator/config.yml` `wiki.extra_dirs:` list of additional project-root dirs (PBJ-style usage `[specs/, decisions/]`) whose `.md` files render under a configurable nav section; (c) flat-knowledge files at `.orchestrator/knowledge/*.md` (no category subdir) under a "Knowledge — Flat" section.

**Why this priority**: P3 because these are pure scanner extensions that do not block the core team-onboarding loop (US-1..US-4) or the M033 grilling integration (US-6). They are load-bearing for the cross-company-collaboration thesis (engagement loop only closes when stage 1–3 artifacts are visible alongside stage 4–5), but that thesis is the post-launch product story, not the launch readiness story. Demoting to P3 lets US-7 ship in the same milestone (right surface, right timing) without blocking US-1..US-6 if scope pressure forces deferral to a post-launch fast-follow.

### User Story 8 — Code-shorthand decorator resolves `M###` / `AP-###` / etc. inline (Priority: P3)

The operator wants the rendered wiki to decorate code shorthand inline: a page that contains `Why: AN-011 + AUD-003 + BG-003` should render as `Why: AN-011 (Analyzer Trust Erosion) + AUD-003 (...) + BG-003 (...)` with each decorated form linking to the term's definition. The decorator runs at build-time, reads a glossary (US-6 if present, else scans the codebase for code-definition patterns), and on each rendered page regex-scans for known patterns (`[A-Z]{2,4}-\d+`, `M\d{3}`, `DR-[A-Z]+-\d+`, `AP-\d+`), rewriting the first occurrence per page as `CODE (Title)` linked to the definition with subsequent occurrences just linked. Patterns that don't resolve are skipped (no broken-link noise).

**Why this priority**: P3 because Finding G calls this the "single biggest readability blocker for cross-company adoption" but **the post-launch wiki-UX-deep proposal** (`.orchestrator/proposals/post-launch-wiki-ux-and-adapters.md`) is the natural home for the decorator — M032's job is the distribution surface and the engagement-loop foundation; the *rendering polish* on top is post-launch fast-follow when real-user signal informs the regex-pattern catalogue. P3 here means "shape it as a stub in M032 so the surface exists, defer the polish to post-launch." If the operator decides during planning that the readability blocker is too hot to defer, US-8 promotes to P2.

**Independent Test**: `tests/m032-acceptance/p0X-code-decorator.sh` against a fixture markdown page: pre-condition: write a page containing `M032 + AP-009 + DR-STACK-001`; pre-condition: write a glossary mapping the three codes to titles; run the decorator → assert each code is rewritten as `CODE (Title)` with a working link, the second occurrence on the page is link-only (no title repeat), and `XYZ-999` (unmapped) is left unchanged.

**Acceptance Scenarios**:

1. **Given** a page containing three known codes and one unknown code, **When** the decorator runs, **Then** the three known codes are decorated and linked, and the unknown code is left byte-identical.
2. **Given** a page containing the same code twice, **When** the decorator runs, **Then** the first occurrence is `CODE (Title)` linked and the second occurrence is `CODE` linked (no title repeat).
3. **Given** US-6's glossary is absent, **When** the decorator runs, **Then** it falls back to scanning the codebase for `### CODE` definition patterns (best-effort) or skips decoration entirely with a debug-level diagnostic.

## Edge Cases

- **Symlink mode on Windows without admin/developer-mode**: Acceptance Scenario US-1.4 — fail closed with "POSIX-only in v1" diagnostic, no silent fallback to copy.
- **`mkdocs gh-deploy -f` invoked from wrong cwd** (Finding J): `wiki-deploy.sh` sanity gate compares `repo_url:` in `mkdocs.yml` against `git remote get-url origin` and fails closed on mismatch (US-4 Acceptance Scenario 2).
- **Giscus category does not exist**: US-3 Acceptance Scenario 4 — fail closed; category creation requires GH Discussions admin scope and is out of scope for v1.
- **`giscus-ids-from-gh.sh` rate-limited by GraphQL**: integration test must mock the helper; a runtime failure from rate-limiting should print the GraphQL error verbatim and exit non-zero (no silent retry loop).
- **Operator removes `custom-nav` markers manually**: US-5 Acceptance Scenario 3 — generator self-heals by re-creating empty markers.
- **Legacy `mkdocs.yml` with `# >>> M012-P01 nav` markers**: US-5 Acceptance Scenario 2 — first regenerate migrates markers to new shape with zero behavior change at empty-custom.
- **`wiki/glossary.md` absent**: US-6 Acceptance Scenario 2 — auto-nav renders without Glossary section, no warning beyond debug-level.
- **Quick-profile context payload requests glossary inject**: US-6 Acceptance Scenario 4 — adapter respects M031 traversal contract, injects only touched terms.
- **`proposals/` entry missing `stage:` frontmatter**: US-7 Acceptance Scenario 1 — render with `stage: unknown` badge; do not exclude.
- **Code shorthand pattern matches but doesn't resolve in glossary or codebase**: US-8 Acceptance Scenario 1 — leave byte-identical (no broken-link noise per Finding G).
- **Project-owned path collides with a staged-asset path**: spec-side invariant per CON-2 below — the manifest's `target:` field must not collide with any file the consumer project owns; collision detected at install time, fail closed with a clear diagnostic naming both sides of the collision.
- **`.orchestrator/installed-files.txt` corrupted or truncated**: installer detects via line-count vs entry-count cross-check; offers `--repair` flag (re-installs from manifest, overwrites tracking file); does not auto-repair.
- **`AGENTS.md` generated alongside `CLAUDE.md` despite `runtime=claude-code`** (Finding A's bilateral-fallback observation; *MIT-009 resolves prior "possibly Finding G_alt" attribution as a distinct runtime-targeted-instruction-file scoping bug, not a M032 finding*): out of scope for M032 (separate bug, defer to runtime-targeted instruction-file scoping work). Document in Open Questions to surface during planning.
