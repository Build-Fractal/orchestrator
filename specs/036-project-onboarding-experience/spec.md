# Feature Specification: 036-project-onboarding-experience

**Feature Branch**: `036-project-onboarding-experience`
**Created**: 2026-05-03
**Last Revised**: 2026-05-03 (post-conversus-gate amendment — folded MIT-001..MIT-007 from `conversus/summary/final.md`)
**Status**: Ready-for-discuss
**Milestone**: M033
**Input**: User description: "M033 Project Onboarding Experience: orchestrator:start warm conversational front door for any new orchestrator-managed project. Branches based on user starting state (greenfield-empty / greenfield-with-materials / existing-codebase / migrating). Always finishes with skills installed, config written, orchestrator-native constitution authored (zero spec-kit dep), CLAUDE.md custom block populated, knowledge graph seeded from materials or codebase, optional wiki/GH integration via M032/M013 gates. Adds three net-new pieces (constitution authoring + codebase ingestion + ideation/materials-intake) and adopts the relentless grilling protocol from mattpocock/skills::grill-with-docs. Pairs with M032 per 2026-05-03 launch sequencing amendment."

## Problem Statement

The orchestrator's `orchestrator:init` is correctly bootstrap-only — four phases (detect → probe → generate → verify) that complete in ~1 second and produce a config + an empty `CLAUDE.md` + installed skills. The 2026-04-28 `pbj-central-mono-repo` bootstrap session proved that this is necessary but nowhere near sufficient: the operator's actual eight-step path from "I want to use the orchestrator" to "ready for `orchestrator:specify` or `orchestrator <task>`" requires (in order) running the install script, running `init`, reading five reference docs, hand-authoring a constitution with no template or scaffold, hand-authoring the CLAUDE.md custom block, manually deciding whether to invoke wiki/GH integrations (no prompts), routing between `orchestrator:specify` vs ideation-from-scratch (no path) vs `orchestrator:migrate`, and then beginning. Several steps require the user to already understand orchestrator's mental model — an adoption tax the launch can't pay against the 2026-05-15 PBJ pilot deadline.

Three concrete pain-points follow. First, **branching state is invisible to today's `init`**: `commands/init.md` runs the same code path whether the user has a spec, a codebase, materials, or nothing — there is no `--interactive` flag and no branch detection, so the four real-world starting states (greenfield-empty / greenfield-with-materials / existing-codebase / migrating) collapse onto one identical empty-project bootstrap. Second, **content authoring is orphaned**: the constitution is referenced by `commands/specify.md` (lines 86, 99, 115) for its Constitution Check section but no orchestrator command authors it; the only available authoring path is `speckit.constitution`, a spec-kit dependency that violates CLAUDE.md's *Standalone Mode* commitment and Principle XVI. Similarly, `templates/project-instruction.md` ships a CLAUDE.md with an empty `<!-- BEGIN CUSTOM --> <!-- END CUSTOM -->` block that no command ever populates, leaving every fresh dispatch to load with zero project context. Third, **knowledge ingestion is spec-shaped only**: `commands/ingest.md` chunks markdown specs into the knowledge graph, but no command ingests an *existing codebase* (README + ARCHITECTURE.md + manifests + directory structure + git log + prior tooling), so M031's universal `orchestrator <task>` entry — which assumes knowledge exists — runs against an empty graph for every existing-codebase project on day one.

The minimum surface that fixes all three is: (a) an `orchestrator:start` sibling command that wraps `init` as one step in a four-branch interactive flow, with branch detection (filesystem probe + ≤2 questions) and per-branch sub-flow stubs that route the operator to the right path; (b) an orchestrator-native `orchestrator:constitution` command + tech-stack-aware starter templates (web-saas / cli-tool / library for v1) that authors `.orchestrator/memory/constitution.md` from a 5–8 question interactive flow with zero spec-kit dependencies; (c) an `orchestrator:ingest-codebase` command that scans top-level docs, package manifests, directory structure, test conventions, recent git log, and prior-tooling artifacts (`.cursor/`, `.aider/`, `.claude/`, `.specify/`, `.gsd/`) to produce 5–15 seed MEM entries; (d) materials-intake + ideation sub-flows for the two greenfield branches that produce `specify`-consumable pre-spec inputs (deterministic drift detection on heterogeneous materials; structured ideation conversation for empty-greenfield); (e) a custom-block drafter that uses the outputs of (a)–(d) to populate CLAUDE.md's `<!-- BEGIN CUSTOM -->` region; (f) integration gates for M032's `--with-wiki` and M013's `--with-github`; (g) the **relentless grilling protocol** (lifted from `mattpocock/skills::grill-with-docs`, MIT) as the conversational shell contract used by P01–P05 — sequential never batched, code-first speculation cap, inline doc updates (writing into `wiki/glossary.md` as terms resolve), surface contradictions live, recommendation-not-interrogation.

This feature explicitly does not redesign the knowledge graph schema (M020's territory, closed), reinvent bundle/install infrastructure (M032's territory — M033 invokes the `--with-wiki` gate), author specs (M033 *invokes* `orchestrator:specify`), implement migration logic (M033 *routes* to existing `orchestrator:migrate`), build the universal small-task entry (M031's territory, closed), introduce model-selection logic (M030's territory, closed), or ship a persistent interactive shell (`start` is one command that runs to completion and exits). It also explicitly does not include profile-driven onboarding ("I'm a senior dev, skip the explanations"), multi-language i18n, cloud/team multi-user setup, or migration from non-spec-kit/GSD tools (Aider, Cursor, generic scaffolds — demand-driven post-launch).

## User Scenarios & Testing *(mandatory)*

### Minimal Slice (Phase 1 Load-Bearing Scope)

The smallest coherent subset that closes the launch first-impression dogfood loop is **US-1 + US-2**: branch-detecting `orchestrator:start` skeleton (US-1) + orchestrator-native `orchestrator:constitution` (US-2). With these two stories shipped, every first-time user can land in a project that has skills installed, config written, branch-correct routing, AND a stack-appropriate constitution authored — the irreducible minimum for `orchestrator:specify`'s Constitution Check (`commands/specify.md:86,99,115`) to gate against real content rather than degrading silently. Subsequent stories (codebase ingestion, materials intake, ideation, custom-block drafter, integration gate pass-through, friendly-tester sign-off) defend on top of this slice — each is independently shippable but assumes the slice exists.

### User Story 1 — `orchestrator:start` skeleton with four-branch routing front door (Priority: P1)

A first-time operator running `orchestrator:start` against a fresh project today has no warm path: they must run `init` (1 second, empty CLAUDE.md), then read five reference docs, then decide which of `orchestrator:specify` / ideation / `orchestrator:migrate` / hand-authoring matches their starting state. The operator wants `bash scripts/lifecycle/start.sh --project-dir <path>` to: (a) probe the filesystem for branch signals (presence of source files + git history → existing-codebase; presence of `.gsd/` / `.specify/` → migrating; presence of project-root `.md` materials → greenfield-with-materials; otherwise greenfield-empty), (b) confirm or correct the detected branch with ≤2 questions following the grilling protocol (sequential, recommendation-not-interrogation), (c) invoke `orchestrator:init` as one step in the flow (preserving init's idempotency contract), (d) route to the branch-specific sub-flow stub, and (e) exit cleanly leaving the project ready for the next sub-flow phase. Branch detection failures (ambiguous signals — e.g., a repo with both `package.json` and partial `.orchestrator/`) MUST ask the user rather than silently picking a default (per Finding A's recommendation; branch detection is high-leverage and getting it wrong costs the whole flow).

**Why this priority**: P1 because every other story in this spec consumes the routing front door — without US-1, US-3 (codebase ingestion) has no triggering branch, US-4 (materials intake) has no triggering branch, US-5 (ideation) has no triggering branch, and US-7 (custom-block drafter) has no upstream sub-flow outputs to draft from. US-1 is also the *first impression* that defines whether new users adopt the orchestrator — every adoption-tax minute beyond minute zero is a step closer to a bounced user. The four-branch contract is also the testable surface for the friendly-tester pass (US-8) that the 2026-05-03 launch sequencing amendment makes load-bearing for milestone close.

**Independent Test**: `tests/m033-acceptance/p01-start-branch-routing.sh` against four fixture projects (one per branch shape, see Edge Cases for fixture inventory): for each fixture, run `bash scripts/lifecycle/start.sh --project-dir <fixture> --yes` → assert the detected branch matches the fixture's intended shape, assert `init-project.sh` was invoked exactly once (`init` runs idempotently), assert the per-branch sub-flow stub printed its "would-execute" diagnostic to stdout (no real sub-flow execution at this story's scope), assert exit code is 0; rerun without `--yes` and assert the branch-detection question fires when the filesystem signal is ambiguous (use a fifth fixture with both `package.json` and `.gsd/` artifacts).

**Acceptance Scenarios**:

1. **Given** a fresh fixture project with no source files, no `.git/`, no project-root `.md` materials, **When** `start --project-dir <fixture> --yes` runs, **Then** the detected branch is `greenfield-empty`, `init` is invoked exactly once, and the ideation sub-flow stub prints its "would-execute" diagnostic.
2. **Given** a fixture project with `package.json` + `src/` + `.git/` + non-empty git log, no `.gsd/`/`.specify/`, **When** `start` runs, **Then** the detected branch is `existing-codebase`, `init` is invoked exactly once, and the codebase-ingestion sub-flow stub prints its "would-execute" diagnostic.
3. **Given** a fixture with three project-root `.md` files (e.g., `PRODUCT-BRIEF.md`, `MVP-PLAN.md`, `DECISIONS.md`) and no source files, **When** `start` runs, **Then** the detected branch is `greenfield-with-materials`, `init` is invoked exactly once, and the materials-intake sub-flow stub prints its "would-execute" diagnostic.
4. **Given** a fixture with `.gsd/v1-roadmap.yml` + `.specify/specs/`, **When** `start` runs, **Then** the detected branch is `migrating`, `init` is invoked exactly once, and the routing message points the operator at `orchestrator:migrate` with the appropriate `--from gsd-v1|spec-kit|gsd-v2` flag pre-filled.
5. **Given** a fixture with ambiguous signals (`package.json` + `.gsd/v1-roadmap.yml`), **When** `start` runs without `--yes`, **Then** the command emits a single grilling-protocol-shaped question asking the operator to disambiguate (recommendation default offered; one-keystroke accept), waits for the answer, and proceeds with the operator-confirmed branch.

### User Story 2 — Orchestrator-native `orchestrator:constitution` authoring with stack starters (Priority: P1)

An operator on a fresh project who wants `orchestrator:specify`'s Constitution Check to gate against real content today must either hand-author `.orchestrator/memory/constitution.md` from scratch (no template, no scaffold) or invoke `speckit.constitution` (a spec-kit dependency that contradicts CLAUDE.md's *Standalone Mode* commitment and Principle XVI). The operator wants `bash scripts/lifecycle/constitution-author.sh --stack <stack> --project-dir <fixture>` to: (a) load `templates/constitution-starters/<stack>.md` (v1 ships **3 starters**: `web-saas`, `cli-tool`, `library` — see Open Questions #Q-2 for the demand-driven expansion path), (b) run a 5–8 question grilling-protocol-shaped interactive flow (sequential, recommendation-not-interrogation, code-first speculation cap that reads detected manifests/structure first), (c) substitute placeholders (`{{project_type}}`, `{{primary_constraint}}`, etc.) into the starter, (d) hand control to the operator's editor for a final review pass (the *every constitution is user-edited before write* discipline from the brief's "Out of scope" section), and (e) write the reviewed file to `.orchestrator/memory/constitution.md`. The command MUST be idempotent under `--force` (re-running preserves operator edits when no `--force`; overwrites cleanly when `--force`).

**Why this priority**: P1 because the constitution is referenced by `commands/specify.md:86,99,115` for the Constitution Check section that gates every spec; without an orchestrator-native authoring path, every first-time user either (a) skips constitution authoring (specify gate degrades silently) or (b) leans on `speckit.constitution` (violates standalone posture). Both failure modes block the launch's first-impression promise. P1 also reflects that this is **Principle XVI's first content-authoring compliance test** — M032 covers asset-distribution surface integrity; M033/US-2 covers the parallel content-authoring surface that, if it leaks to spec-kit, breaks the standalone-launch story. The starter-library shape (3 stacks for v1) is the deliberate Constitution-XIV "no speculative complexity" choice — Open Questions #Q-2 surfaces the expansion criterion.

**Independent Test**: `tests/m033-acceptance/p02-constitution-author.sh` against three fixture projects (one per starter stack): for each, set `EDITOR=cat` to bypass the interactive editor pass; run `bash scripts/lifecycle/constitution-author.sh --stack <stack> --project-dir <fixture> --yes` → assert `<fixture>/.orchestrator/memory/constitution.md` exists, assert it contains the stack-specific principles named in the starter (e.g., web-saas adds *Idempotent Deploys*; cli-tool adds *Composable Default Exit Codes*; library adds *Stable API Surface*), assert all `{{...}}` placeholders are resolved (no literal `{{` strings remain), and assert the file passes `bash scripts/verify/constitution-shape-lint.sh <path>` (a new lightweight verifier asserting required principle headers + non-empty body sections). Re-run with `--force` and assert the file is regenerated cleanly; re-run without `--force` and assert the file is preserved with a "no-changes" diagnostic. **Standalone gate**: assert zero `speckit.*` references in any output (stdout, stderr, written file).

**Acceptance Scenarios**:

1. **Given** a fresh fixture project with no `.orchestrator/memory/constitution.md`, **When** the operator runs `constitution-author --stack web-saas --yes`, **Then** the file is written, contains the 6–8 baseline principles + 2–3 web-saas-specific principles named in the starter (`Idempotent Deploys`, `User Data Privacy`, etc.), and `grep -i 'speckit' <output>` returns no matches.
2. **Given** an existing `<fixture>/.orchestrator/memory/constitution.md`, **When** the operator re-runs `constitution-author` without `--force`, **Then** the file is preserved byte-identical and the command exits 0 with a "no changes" diagnostic.
3. **Given** an existing constitution and `--force`, **When** the operator re-runs, **Then** the file is regenerated from the starter template and the previous content is overwritten (warning printed to stderr that `--force` discards prior edits).
4. **Given** an unknown `--stack` value (e.g., `--stack quantum-mainframe`), **When** the command runs, **Then** it exits non-zero with a clear diagnostic listing the v1 supported stacks (`web-saas`, `cli-tool`, `library`) and pointing at Open Questions #Q-2 for the expansion path.
5. **Given** the operator answers all 5–8 grilling questions but the editor pass produces a file missing a required principle header, **When** the verifier runs, **Then** the command exits non-zero with the missing-header name (operator can re-invoke and re-edit; no silent partial-write).

### User Story 3 — `orchestrator:ingest-codebase` seeds knowledge graph from existing repo (Priority: P1)

An operator running `orchestrator:start` against an existing-codebase fixture today gets routed to the existing-codebase branch (US-1) but the project's knowledge graph remains empty — `commands/ingest.md` ingests *spec markdown* only, leaving M031's universal `orchestrator <task>` entry on day one with zero MEMs to inject into payloads. The operator wants `bash scripts/lifecycle/ingest-codebase.sh --project-dir <fixture>` to scan: (a) top-level docs (`README.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, `docs/`), (b) package manifests (`package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, etc.) — extract dependencies, scripts, project-type signals, (c) directory structure (top 2 levels of `src/` or equivalent — infer module boundaries), (d) test directory shape — infer testing conventions, (e) recent git log (last ~50 commits) — infer active areas + contributor patterns, (f) prior tooling artifacts (`.cursor/`, `.aider/`, `.claude/`, `.specify/`, `.gsd/`) — detect prior toolchain state. From these signals the command produces 5–15 seed MEM entries under `knowledge/architecture/`, `knowledge/conventions/`, `knowledge/decisions/` (M020's existing graph schema, no new kinds). The scan is **deterministic structural extraction**, not semantic understanding (Open Questions #Q-3 surfaces the LLM-augmentation expansion path as M033.5 demand-driven). The command MUST be idempotent: re-runs detect existing seed MEMs by their stable IDs and emit a `re-ingest` diagnostic rather than producing duplicates.

**Why this priority**: P1 because **without US-3, the existing-codebase branch from US-1 routes the operator to a sub-flow that produces an empty knowledge graph** — exactly the failure mode that breaks M031's "every dispatch is knowledge-rich" promise on day one for every existing-codebase project. The brief's Finding A 2026-04-29 dogfood addendum is the empirical signal: rich architectural context already on disk at `.orchestrator/DECISIONS.md` (DR-MILESTONE-001, DR-RECONCILE-001..005, DR-PROCESS-001..004) is *substance-equivalent* to a finalized `M###-CONTEXT.md`, but no command surfaces it. US-3 codifies the **import-from-existing** path that closes this gap: detect rich-context source files (`DECISIONS.md` with `DR-` entries, `MILESTONE-AUDIT.md`, `CLAUDE.md` custom blocks) AND offer a non-interactive import path that emits a thin `M###-CONTEXT.md` with `context_source: imported-from-existing` pointing at those sources — preserves the file-shape contract for downstream tools (no roadmap gate change needed) without forcing re-litigation of context the project has already finalized. P3 collapse condition (per the brief): if the P00 friendly-tester pass shows existing-codebase users tolerate manual KB seeding through M031's universal entry organically, US-3 collapses to a stub that drafts 1–2 placeholder MEMs from README only, recovering ~1 week of milestone budget.

**Independent Test**: `tests/m033-acceptance/p03-ingest-codebase.sh` against three fixture projects (one per ~stack variant: TypeScript SaaS, Python CLI, Rust library): for each, run `bash scripts/lifecycle/ingest-codebase.sh --project-dir <fixture>` → assert ≥5 and ≤15 MEM entries are written under `<fixture>/.orchestrator/knowledge/{architecture,conventions,decisions}/`, assert each MEM has a stable ID derivable from its source path (re-run produces zero new entries), assert the rich-context import path fires when `<fixture>/DECISIONS.md` is present (a thin `M###-CONTEXT.md` with `context_source: imported-from-existing` is emitted), and assert `bash scripts/dispatch/build-context.sh --profile=quick --task "fix flaky <test-name>"` against the post-ingest fixture loads ≥3 of the seeded MEMs into the payload (proves the seeded graph is consumable by M031's entry path).

**Acceptance Scenarios**:

1. **Given** a TypeScript SaaS fixture with `package.json` + `src/` + `tests/` + `README.md` + `ARCHITECTURE.md`, **When** `ingest-codebase` runs, **Then** ≥5 MEMs are produced (at least one per category: architecture from directory structure, convention from package.json scripts, decision from README technical-decisions section).
2. **Given** the same fixture re-run after the first ingest, **When** `ingest-codebase` runs again, **Then** zero new MEMs are produced and the command emits a `re-ingest: <N> existing entries detected, no changes` diagnostic; exits 0.
3. **Given** a fixture with `.orchestrator/DECISIONS.md` containing `DR-` entries, **When** `ingest-codebase` runs, **Then** the rich-context import path fires, a `M###-CONTEXT.md` is emitted at `.orchestrator/milestones/M###/` with `context_source: imported-from-existing`, AND the `DR-` entries are surfaced as `knowledge/decisions/MEM-DR-*` MEMs (cross-reference, not duplicate authoring).
4. **Given** a fixture with `.gsd/v1-roadmap.yml` (migration territory) AND a populated `src/`, **When** the operator first ran `start` (US-1) and was routed to `migrating` (per US-1 AS-4), **Then** `ingest-codebase` is **not** auto-invoked; the operator first completes `orchestrator:migrate`, then optionally invokes `ingest-codebase` to fill gaps the migration didn't cover. Verifier: no duplicate MEMs across the migrate-then-ingest path (per brief Open Questions #Q-10).
5. **Given** a fixture with no `README.md`, no `ARCHITECTURE.md`, no manifests (degenerate "source files only" repo), **When** `ingest-codebase` runs, **Then** it produces the minimum viable seed (≥1 MEM derived from directory structure alone) and emits a stdout diagnostic listing what was missing (gives the operator a checklist of what would have improved the seed).

### User Story 4 — Materials intake with deterministic drift reconciliation for greenfield-with-materials (Priority: P2)

An operator arriving with heterogeneous source materials (Product Brief, Decision Register, MVP Plan, Handoff JSON, milestone audits identifying inconsistencies — the named PBJ-shape) today has no orchestrator command to intake those materials, reconcile drift across them, and produce a unified `orchestrator:specify`-consumable input. The operator does this by hand across multiple sessions, leaking the highest-leverage adversarial-review and Constitution-Check moments to ad-hoc tooling. The operator wants `bash scripts/lifecycle/materials-intake.sh --project-dir <fixture>` to: (a) enumerate detected materials in the project directory (markdown, PDF via `textutil`, JSON, plain text), (b) run a grilling-protocol-shaped sequential question loop asking the operator to label each (*primary spec*, *supplementary*, *decision history*, *out-of-scope reference*), (c) run **deterministic cross-document drift detection** — check for ID misalignment, scheme contradictions, orphan references (no LLM-magic merge), (d) surface drift findings as a checklist with one entry per conflict; the operator resolves each (accept primary, accept supplementary, manual edit, defer), and (e) produce a reconciled spec input file at `.orchestrator/intake/<timestamp>/reconciled-pre-spec.md` that `orchestrator:specify` can consume verbatim. Reconciliation UX is terminal-interactive for ≤5 conflicts; for >5, hand off to a single markdown checklist file the operator edits and re-invokes (per brief Open Questions #Q-6; PBJ has 5 — on the boundary).

**Why this priority**: P2 because greenfield-with-materials is the second-most-common starting state (not the most-common — that's existing-codebase per launch posture) but is the highest-stakes branch when it triggers (PBJ-shape projects have already invested significant authoring effort; silent drift in those materials cascades into spec-shaped bugs that compound through every downstream phase). P2 reflects that some launch users will arrive with a single `README.md` and skip materials-intake entirely (greenfield-empty branch handles them via US-5 ideation), but the users who *do* arrive with PBJ-shape materials need US-4 to land or they fall back to the current pain (hand-reconciliation across multiple sessions — exactly the friction the launch is trying to remove). The deterministic-not-LLM choice is Constitution-XIV (no speculative complexity) discipline — the operator stays in control of every conflict.

**Independent Test**: `tests/m033-acceptance/p04-materials-intake.sh` against the **PBJ-shape fixture** (`tests/fixtures/m033-pbj-materials-fixture/` — a curated synthetic version of the 2026-04-28 PBJ materials with the same 5 known inconsistencies preserved): pre-condition: drop the fixture materials into a fresh project; run `bash scripts/lifecycle/materials-intake.sh --project-dir <fixture> --yes` (with `--yes` auto-accepting the labeling defaults) → assert the deterministic drift detector surfaces all 5 known inconsistencies as a checklist, assert the operator resolution loop accepts terminal-interactive answers for the first 5, assert the resulting `<fixture>/.orchestrator/intake/<timestamp>/reconciled-pre-spec.md` is byte-deterministic (same fixture + same answers → same output), and assert `orchestrator:specify --description "$(cat <reconciled-pre-spec.md>)" --yes` runs cleanly against the reconciled output.

**Acceptance Scenarios**:

1. **Given** the PBJ-shape fixture with 5 known inconsistencies, **When** `materials-intake --yes` runs, **Then** the drift detector surfaces exactly 5 conflicts (no false positives, no false negatives) as a numbered checklist.
2. **Given** the operator selects "accept primary" for all 5 conflicts, **When** the reconciliation loop completes, **Then** the reconciled pre-spec file resolves each conflict in favor of the operator-labeled primary spec and emits a one-line provenance comment per resolution (`<!-- Reconciled: conflict-N → accept-primary -->`).
3. **Given** a fixture with >5 conflicts (synthetic, ~8 conflicts), **When** the loop hits the boundary, **Then** the command writes a markdown checklist to `<fixture>/.orchestrator/intake/<timestamp>/conflicts.md` and exits 0 with a "edit then re-invoke with --resolve <conflicts.md>" diagnostic (defers to file-based UX per #Q-6).
4. **Given** the PBJ fixture missing one of the 5 inconsistencies (operator manually pre-resolved it), **When** `materials-intake` runs, **Then** the detector surfaces 4 conflicts (not 5) and proceeds normally — proves the detector reads current state, not a hardcoded count.
5. **Given** a fixture with **only** out-of-scope reference materials (operator labels every detected file as `out-of-scope`), **When** the loop completes, **Then** the command exits 0 with a "no primary spec materials labeled — skipping reconciliation, falling back to greenfield-empty ideation flow" diagnostic, and routes the operator to US-5 (ideation) rather than producing an empty pre-spec.

### User Story 5 — Greenfield-empty ideation produces structured pre-spec (Priority: P2)

An operator arriving with "I have an idea, nothing else" today has no orchestrator entry path: `commands/specify.md` requires a feature description to scaffold from, so users either bounce off the orchestrator (worst case) or write their pre-spec elsewhere (the leak point — pre-spec writing is *exactly* where the orchestrator's adversarial-review and Constitution-Check value compounds most). The operator wants `bash scripts/lifecycle/ideation.sh --project-dir <fixture>` to run a grilling-protocol-shaped sub-conversation walking through: (a) problem statement, (b) target user, (c) MVP boundary, (d) top-3 user stories, (e) primary success metric, (f) top-3 risks, (g) top-3 non-goals — emitting a structured pre-spec markdown doc to `<fixture>/.orchestrator/intake/<timestamp>/ideation-pre-spec.md` that `orchestrator:specify` consumes as if it were user-authored materials. Optional `--with-conversus-stress-test` flag composes with conversus for adversarial idea-stress-testing on the produced pre-spec (default off per brief Open Questions #Q-7 — token cost is real; ideation should be cheap by default).

**Why this priority**: P2 (not P1) because greenfield-empty is the lowest-volume starting state at launch (users are generally arriving with *some* signal — either materials or an existing codebase) AND because the "I have an idea" user can also reach `orchestrator:specify` directly with a hand-written description (degraded path exists). US-5 elevates the experience from "you can technically use the orchestrator" to "the orchestrator collects your idea structurally before authoring" — a real win, but the lowest-priority of the four branch sub-flows. P2 also reflects that the ideation conversation can collapse to ~7 questions in a single session, reusing the same grilling-protocol shell as US-2 and US-4, so implementation cost is lower than the comparable surface for materials intake.

**Independent Test**: `tests/m033-acceptance/p04-ideation.sh` against a fresh empty fixture: pre-condition: empty fixture project; pre-script answers to 7 ideation questions via stdin redirection; run `bash scripts/lifecycle/ideation.sh --project-dir <fixture> --yes < <answers-file>` → assert `<fixture>/.orchestrator/intake/<timestamp>/ideation-pre-spec.md` exists, assert it contains all 7 sections (Problem / Target User / MVP / User Stories / Success Metric / Risks / Non-Goals), assert each section is non-empty, and assert `orchestrator:specify --description "$(head -200 <ideation-pre-spec.md>)" --yes` runs cleanly against the output.

**Acceptance Scenarios**:

1. **Given** an empty fixture and pre-recorded answers to all 7 ideation questions, **When** `ideation --yes` runs against stdin, **Then** the output file contains all 7 sections in the documented order with the operator's verbatim answers in place.
2. **Given** the operator skips a question (presses enter at a recommendation default), **When** the loop completes, **Then** the output section uses the recommendation default verbatim and a `<!-- Recommended-default-accepted -->` provenance comment is inline.
3. **Given** `--with-conversus-stress-test` is passed, **When** ideation completes, **Then** the conversus adapter is invoked against the produced pre-spec and any adversarial findings are appended as an `## Adversarial Findings (deferred to specify)` section in the output file.
4. **Given** `--with-conversus-stress-test` is **not** passed, **When** ideation completes, **Then** zero conversus invocations are logged in `.orchestrator/execution-log.jsonl` (proves opt-in default per #Q-7).

## Edge Cases

- **Branch detection ambiguity**: US-1 AS-5 — surface as a single grilling-protocol question with a recommendation default; never silently pick.
- **`git init` before `orchestrator:start` on an empty project** *(per MIT-006)*: rule 3 (`.git/` with ≥1 commit) fires, routed to `existing-codebase`. The disambiguation question from US-1 AS-5 SHOULD fire for this case when the project has ≤9 source files and no prior-tooling artifacts, offering `greenfield-empty` as the recommended branch. The friendly-tester pass (SC-15) is the empirical signal for whether this disambiguation question is sufficient — if ≥1 eligible tester reports the git-init-before-start routing as a `friction_blocker`, FR-2's rule 3 `.git/ with ≥1 commit` clause should be reconsidered (e.g., narrowed to "`.git/` with ≥1 commit AND (`src/` present OR ≥5 source files)").
- **`init` already ran on the project before `start` is invoked**: `start` MUST detect and skip `init` re-invocation (idempotency); print a "init already complete, proceeding to branch sub-flow" diagnostic.
- **User aborts mid-flow** (Ctrl+C between sub-flows): `start` MUST leave the project in a defined partial state — `init` outputs (if `init` ran) preserved, sub-flow outputs (if any sub-flow started) preserved, no rollback. Re-invocation of `start` MUST detect the partial state and resume from the last completed sub-flow rather than restarting from US-1.

- **Codebase scan against a 100k-LOC monorepo** (US-3 unbounded scan): the scan MUST cap depth at top 2 levels per the brief; a `--scan-depth N` flag is reserved for future demand-driven expansion. P3-collapse condition (brief): if friendly-tester pass shows the deterministic seed is too thin on real codebases, the LLM-augmentation path becomes M033.5 (out of M033 scope).
- **Materials intake against a directory with binary materials** (PDF, images): US-4 detects via file extension; PDF is converted via `textutil` on darwin and `pdftotext` on linux; images are skipped with a stdout diagnostic (not silently dropped). Missing converter binary is detected and surfaced as a diagnostic, not silently skipped.
- **Materials intake with a `>5 conflicts` count** (US-4 AS-3): the conflict count threshold for terminal-vs-file UX is configurable via `M033_CONFLICT_FILE_THRESHOLD` (default 5 per #Q-6); the threshold value is logged to `.orchestrator/execution-log.jsonl` so retrospectives can tune it.

- **`M033_SKIP_FRIENDLY_TESTER_PASS=1` opt-out**: US-8 AS-5 — explicit escalation path; signed attestation in `M033-SUMMARY.md`; the milestone closes with documented cold-start risk acknowledged.
- **`AGENTS.md` generated alongside `CLAUDE.md` despite `runtime=claude-code`** (Finding A from spec 035 / NG-11 from spec 035): out of scope for M033 (separate runtime-targeted-instruction-file scoping bug); document in Open Questions to surface during planning so the custom-block drafter (US-7) doesn't silently dual-write to `AGENTS.md` when the runtime is `claude-code`-only.
