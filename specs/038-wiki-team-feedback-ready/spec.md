## Problem Statement

After M032 closed (2026-05-05) plus papercut-sweep rounds 1+2, every orchestrator-managed wiki renders cleanly under `mkdocs build --strict`. PBJ-central round-3 dogfood (2026-05-06) exercised the resulting wiki against its actual intended audience — non-author domain SMEs and occasional contributors — and surfaced a different class of issue: the wiki is *correctly built but not yet usable for a non-author reader*. The current state would convert the next two weeks of PBJ-team review (the live dogfood signal for the entire orchestrator process) from "is the orchestrator's process right?" into "the wiki is unusable", contaminating exactly the validation loop M035-launch is supposed to ride into release.

Three concrete pain-points produce that contamination on first contact. First, **the homepage is an operator README, not a clickable map**: `/` reads as developer-onboarding prose ("How to navigate", "Where to comment", "Deploy & preview") instead of a card grid that points a domain SME at the content the operator wants feedback on. Second, **reference and decision navigation reads as code-soup, not human concepts**: the reference nav surfaces 70+ entries titled `REF-cms-rule-cms-qso-21-06-nh-2020-12`-shaped slugs even though the source chunks carry human-readable `version:` frontmatter, and the `/decisions/` right-side TOC reads as a list of `DR-CODE-NNN` codes because the heading shape leads with the code rather than the concept. Third, **top-level surfaces are buried in a sidebar with `####`-deep TOCs and no edit/source-link affordance**, so a reader who finds something out-of-date has no obvious path to surface that signal.

The minimum surface that fixes all three on first impression is: (a) a homepage card-grid template + `wiki.landing_cards:` config schema fed from project-defined cards (defaults derived from top-level nav sections); (b) `wiki-generate-stubs.sh` reading source chunk `version:` frontmatter into stub `title:` so reference nav reads as human strings; (c) an authoring convention that pivots `### DR-CODE-NNN — Title` to `### Title { #dr-code-nnn }` with the code rendered as a body chip, applied retroactively to this repo's own `DECISIONS.md` and promoted via `references/` doc + `commands/dispatch.md` payload guidance; (d) trivial `mkdocs.yml` template additions — `navigation.tabs` + `navigation.tabs.sticky`, `toc.toc_depth: 2`, `content.action.edit` + `edit_uri` derived from `repo_url`; (e) the install-template `config.yml` clobber fix from `.orchestrator/proposals/install-template-preserve-operator-keys.md`, bundled into M037 because we are already touching template territory and the operator pain-point (`wiki:` config block clobbered on every `orchestrator:update`) is in M037's path.

This feature explicitly does not redesign the `include-markdown` architecture (round-2 settled it), eliminate `DR-### / MEM-### / BG-###` codes from source content (codes are load-bearing for cross-references and grep-ability — fix is presentation, not removal), rename source-side `version:` frontmatter to `title:` (read at projection time, do not churn the source schema), build a knowledge-graph viewer or faceted search (`wiki-ux-deep` post-launch proposal owns those), or add external-tool adapters (`external-tool-adapters` post-launch proposal). It also does not address validator-audience polish — that is round 4, after PBJ team's first feedback signal lands.

## User Scenarios & Testing *(mandatory)*

### Minimal Slice (Phase 1 Load-Bearing Scope)

The smallest coherent subset of user stories that closes the dogfood loop is **US-1 + US-2 + US-4 + US-11**: a non-author reader landing on `/` sees a card grid pointing at the content sections (US-1), the reference nav reads as human strings rather than slug-soup (US-2), top-level navigation is visually first-class with a scannable TOC and an edit affordance (US-4), and the publishing pipeline reliably delivers content changes to the live site (US-11 — without F12's workflow-based publishing, a stuck legacy `pages-build-deployment` builder can wedge content updates indefinitely, so any reader-side improvement is gated by the deploy primitive). With these four stories shipped, the PBJ team's review feedback returns signal about *the orchestrator's process and content* rather than about *the wiki's chrome* or *whether the deploy made it live*. US-3 (DR-### heading-shape), US-5 (install-template clobber fix), US-10 (F8 feedback routing), US-12 (F13 private-repo `site_url`), US-13 (F10 OUT-OF-SCOPE collapse), and US-14 (F11 README discussions callout) ride P01 alongside the slice because they are small surfaces, share the template/init-territory cost, and address operator pain that PBJ team has already filed. P02's stories (US-6..US-9) are defended on top of US-1..US-5 + US-10..US-14 once PBJ's first feedback signal informs the bucket-mapping and section-shape choices.

### User Story 1 — Homepage card grid replaces operator README (Priority: P1)

A non-author reader (PBJ domain SME, validator pilot, occasional contributor) opens `/` of an orchestrator-managed wiki today and reads developer-onboarding prose instead of seeing a clickable map of sections. The operator wants `/` to render as a mkdocs-material `grid cards` block with project-defined cards (icon + title + blurb + section link) so the reader's first second on the wiki points them at the content the operator wants feedback on. The cards are config-driven via a new `wiki.landing_cards:` schema in `.orchestrator/config.yml`; when the project has not customized the schema, defaults derive from the top-level nav sections that `wiki-generate-nav.sh` enumerates, with generic blurbs keyed on section name.

**Why this priority**: P1 because the homepage is the reader's first visual surface; if it fails, every downstream improvement is filtered through that first impression. The card grid is also the load-bearing primitive for US-8 (`/knowledge/` card grid) — landing it once in M037 means US-8 reuses the template rather than reinventing it.

**Independent Test**: `tests/m037-acceptance/p01-card-grid-homepage.sh` against a synthetic fixture with a known `wiki.landing_cards:` block: render `wiki/docs/index.md` via the projection script → assert the rendered HTML contains a `<div class="grid cards">` block, one card per declared schema entry, with the configured icon + title + blurb + section href; run a second fixture without `wiki.landing_cards:` → assert defaults derive from the top-level nav sections (one card per section with a generic blurb).

**Acceptance Scenarios**:

1. **Given** a project with `wiki.landing_cards:` declared in `.orchestrator/config.yml` and the M037 stub generator run, **When** `mkdocs build` runs, **Then** `/index.html` contains a `grid cards` block with one card per declared entry and each card href resolves to a real top-level nav section.
2. **Given** a project with no `wiki.landing_cards:` configuration, **When** the generator runs, **Then** default cards are emitted (one per top-level nav section, generic blurb keyed on section name) and `mkdocs build` completes with no warnings.
3. **Given** a project's `wiki.landing_cards:` declares a `section:` value that does not match any top-level nav section, **When** the generator runs, **Then** the card is rendered with a placeholder href and a build-time diagnostic identifies the orphan card without failing the build.
4. **Given** a project re-runs `orchestrator:update` after customizing `wiki.landing_cards:`, **When** the install-template refresh fires, **Then** the operator-authored `wiki.landing_cards:` block survives the refresh (per US-5).

### User Story 2 — `version:` → nav title rewrites slug-soup as human strings (Priority: P1)

PBJ-central currently has 70+ entries in the reference-corpus nav titled `REF-cms-rule-cms-qso-21-06-nh-2020-12`-shaped slugs. The source chunks carry human-readable `version:` frontmatter (e.g., `"QSO-21-06-NH (December 4, 2020)"`); the projection layer ignores it. The operator wants `scripts/wiki/wiki-generate-stubs.sh` to read each source chunk's `version:` field at stub-generation time and set the stub's frontmatter `title:` to that value (with deterministic fallback to the chunk-id slug when `version:` is absent). `wiki-generate-nav.sh` already honors stub `title:` when present; if it does not, that pass-through is taught here. The fix narrows the same shape across regulatory-doc / training-material / glossary nav sections — every reference family gets the same upgrade in one pass.

**Why this priority**: P1 because reference nav is the second visual surface a reader hits after the homepage. A reader scanning a 70-entry sidebar list of slugs cannot find anything; the same list rendered as `version:` strings becomes scannable. This story has the highest signal-density-per-byte of any P01 story — touching one script restores readability across the whole reference surface.

**Independent Test**: `tests/m037-acceptance/p01-version-to-nav-title.sh` against a synthetic chunk corpus under `tests/fixtures/m037-version-projection/`: pre-condition: write three chunks — one with `version: "Human Label A"`, one with `version: "Human Label B"`, one with no `version:` field; run `wiki-generate-stubs.sh --root <fixture>`; assert the stubs emitted carry `title: "Human Label A"` / `title: "Human Label B"` / `title: <chunk-id-slug-fallback>`; run `wiki-generate-nav.sh --root <fixture>`; assert the rendered nav YAML lists the human strings (and the slug for the absent-`version:` case).

**Acceptance Scenarios**:

1. **Given** a source chunk with `version: "QSO-21-06-NH (December 4, 2020)"` in frontmatter, **When** the stub generator runs, **Then** the emitted stub's frontmatter contains `title: "QSO-21-06-NH (December 4, 2020)"`.
2. **Given** a source chunk with no `version:` field, **When** the stub generator runs, **Then** the emitted stub falls back to the chunk-id slug as `title:` and emits a diagnostic at debug level (no warning escalation).
3. **Given** the orchestrator's own reference corpus and PBJ-central's reference corpus, **When** the generator runs end-to-end, **Then** the rendered nav YAML for both projects shows the `version:` string in place of the chunk-id slug (no orchestrator-specific behavior; the fix generalizes).
4. **Given** an operator manually edits a stub's `title:` after generation, **When** the generator re-runs (idempotency check), **Then** the operator edit is preserved if and only if the stub carries an `auto_generated: false` marker (otherwise re-derived from source `version:` per generator contract — the marker convention is the operator's escape hatch).
5. *(theme-leverage amendment)* **Given** Material's built-in `Typeset` plugin advertises "preserves formatted titles and headlines in navigation and table of contents", **When** the FR-5 implementing task begins, **Then** the executor MUST first evaluate (≤ 1 hour, time-boxed) whether enabling Typeset plugin alone subsumes FR-5's `version:` → `title:` projection logic for our use case (chunks with `version:` frontmatter, not source-side title formatting). If Typeset solves it: scope FR-5 down to a 1-line plugin enable + idempotency-test for the `auto_generated: false` escape hatch. If Typeset does NOT solve it (likely outcome — Typeset operates on heading-text formatting, not on frontmatter-field projection): FR-5 ships as originally planned and the evaluation outcome is recorded in the task summary. The evaluation gate exists to catch reinventing-the-wheel risk before the executor authors duplicate logic.

### User Story 3 — DR-### heading-shape pivot makes decisions TOC scannable (Priority: P1)

A reader opens `/decisions/` on any orchestrator-managed project and the right-side TOC renders as a list of `DR-CODE-NNN` codes — the human-readable label trails the dash and the reader's eye cannot find an anchor. The operator wants the heading shape pivoted from `### DR-CODE-NNN — Human title` to `### Human title { #dr-code-nnn }` so the TOC reads as scannable concepts and the code is rendered as a body chip (small permalink-style suffix) underneath the heading, preserving stable URLs via `attr_list` anchor. The pivot applies retroactively to this repo's own `.orchestrator/DECISIONS.md` (load-bearing for the orchestrator's own readability) and is promoted as an authoring convention in `references/architecture.md` (or appropriate `references/` doc — exact placement is #Q-3) covering DR-### / BG-### / AN-### / MEM-### / Q-### code conventions. `commands/dispatch.md` payload guidance is updated to reference the convention so artifact-authoring tasks emit decision-log entries in the new shape from day one.

**Why this priority**: P1 because the decisions TOC is the reader's third visual surface (after homepage and reference nav) and one of the most-linked-to surfaces from spec / phase-plan / proposal cross-references. Fixing the heading shape once cascades through every cross-reference path. This story is also content-side and authoring-convention work — small surface area in this repo, large generalization to every consumer project's authoring patterns.

**Independent Test**: `tests/m037-acceptance/p01-dr-heading-shape.sh` against this repo's `.orchestrator/DECISIONS.md`: assert every `### ` heading in the file matches the new shape regex (`^### .+ \{ #(dr|bg|an|mem|q)-[a-z0-9-]+ \}$`); assert no heading matches the legacy shape (`^### (DR|BG|AN|MEM|Q)-[A-Z0-9-]+ — `); render the file via mkdocs and assert the right-side TOC entries are human strings (not codes); assert the body chip pattern (`<span class="code-chip">DR-CODE-NNN</span>` or equivalent) appears immediately below each heading.

**Acceptance Scenarios**:

1. **Given** `.orchestrator/DECISIONS.md` migrated to the new heading shape, **When** the file is rendered via mkdocs, **Then** the right-side TOC reads as human strings and every legacy permalink (`#dr-code-nnn`) still resolves (no broken inbound links from specs / phase-plans / proposals).
2. **Given** the authoring convention is documented in `references/`, **When** an operator authors a new DR entry following the convention, **Then** the entry renders correctly and the pre-merge wiki-build smoke test passes.
3. **Given** `commands/dispatch.md` payload guidance references the convention, **When** a future artifact-authoring task emits a decision-log entry, **Then** the entry uses the new heading shape (verified by spec-shape lint or equivalent verifier — exact verifier surface is #Q-4).
4. **Given** the legacy heading shape persists in any other consumer project (PBJ-central, lakeledger, etc.), **When** that project adopts the convention, **Then** a one-shot rewriter (#Q-3 deferred to planning) is available — rollout strategy across consumer projects is captured in Open Questions, not blocked at spec time.

### User Story 4 — `mkdocs.yml` polish bundle: tabs + toc_depth + edit_uri (Priority: P1)

A reader on an orchestrator-managed wiki today sees top-level sections (Constitution / Decisions / Milestones / Knowledge / Reference) buried in a sidebar; the per-page TOC drills into `####` headings producing visual code-soup; and an out-of-date page offers no edit or view-source affordance to surface the signal. The operator wants three trivial `mkdocs.yml` template changes bundled together because they touch the same file and ship the same impression-quality win: (a) `navigation.tabs` + `navigation.tabs.sticky` in `theme.features` to promote top-level sections to a tabbed header; (b) `toc.toc_depth: 2` to drop `####`-deep TOC entries (granular pages can override per-page via frontmatter when needed); (c) `content.action.edit` + `content.action.view` features plus `edit_uri: edit/main/wiki/docs/` derived per-project from `repo_url` (already in `mkdocs.yml`) at template-emit time.

**Why this priority**: P1 because all three are trivial config changes (single-digit lines each) that land together in one PR, ship together to every consumer project, and produce three visible reader-trust wins simultaneously. Splitting them into separate stories would be process overhead disproportionate to the surface area.

**Independent Test**: `tests/m037-acceptance/p01-mkdocs-polish-bundle.sh` against a freshly initialized fixture: run `bash scripts/lifecycle/wiki-init.sh --project-dir <fixture>` → assert the rendered `<fixture>/wiki/mkdocs.yml` contains `navigation.tabs` + `navigation.tabs.sticky` under `theme.features`, `toc.toc_depth: 2` under markdown extensions, `content.action.edit` + `content.action.view` under `theme.features`, and `edit_uri:` resolving to a value derived from the fixture's git remote (e.g., `edit/main/wiki/docs/`); render the wiki and assert the served HTML contains a tabbed header, a 2-level TOC, and an edit-this-page link on every content page.

**Acceptance Scenarios**:

1. **Given** a fresh fixture with a git remote pointing at `<owner>/<repo>`, **When** `wiki-init` runs, **Then** the rendered `mkdocs.yml` carries the three feature additions and `edit_uri:` evaluates to `edit/<default-branch>/wiki/docs/` derived from the remote.
2. **Given** a project on the legacy `mkdocs.yml` template (pre-M037), **When** the operator runs `orchestrator:update`, **Then** the template refresh adds the three feature additions to the operator's `mkdocs.yml` without overwriting other operator-authored keys (per US-5's clobber fix; see Edge Cases for the merge semantics).
3. **Given** a per-page frontmatter `toc_depth: 4` override on a granular page (e.g., a phase plan), **When** the page is rendered, **Then** the per-page override wins over the global `toc_depth: 2` default.
4. **Given** a project's `repo_url:` is unset in `mkdocs.yml`, **When** the template-emit logic runs, **Then** `edit_uri:` is omitted (no broken edit-link affordance) and a diagnostic is emitted suggesting the operator set `repo_url:`.

### User Story 5 — Install-template `config.yml` clobber fix preserves operator-authored keys (Priority: P1)

PBJ-central re-authors the `wiki:` block in `.orchestrator/config.yml` after every `orchestrator:update` because the install template clobbers the file rather than merging. The operator wants the install-template emission logic for `.orchestrator/config.yml` to preserve operator-authored top-level keys: when a key already exists in the consumer's `config.yml`, the install template MUST NOT overwrite it; when a key is absent, the template MUST add it; orchestrator-owned keys (those scoped under explicit framework-managed namespaces — exact list is #Q-4) are managed by the template and overwritten on refresh. The fix is bundled into M037 because it shares template-territory with US-1 (which introduces a new schema operators will customize and would lose to the same clobber pattern); not bundled into M035 because M035 does not touch `config.yml` template emission and bundling there would expand its surface area.

**Why this priority**: P1 because US-1's `wiki.landing_cards:` schema is itself an operator-customized key — landing US-1 without US-5 would ship a schema operators would lose on every update, surfacing exactly the operator pain US-5 fixes. The two stories share a critical-path coupling that pulls US-5 into P01.

**Independent Test**: `tests/m037-acceptance/p01-config-clobber-fix.sh` against `tests/fixtures/m037-config-merge/`: pre-condition: write a `<fixture>/.orchestrator/config.yml` with operator-authored keys (`wiki.landing_cards:` block + an arbitrary operator-authored top-level key); run the install-template refresh equivalent to `orchestrator:update`; assert the operator-authored keys survive byte-identical and any new orchestrator-managed defaults are added without disturbing operator content.

**Acceptance Scenarios**:

1. **Given** a consumer with a populated `wiki.landing_cards:` block + an arbitrary operator-authored top-level key in `.orchestrator/config.yml`, **When** the install-template refresh runs, **Then** both blocks survive byte-identical and the orchestrator-managed defaults are merged underneath.
2. **Given** a consumer with no `.orchestrator/config.yml`, **When** the install-template emits the file fresh, **Then** the file is created with all orchestrator-managed default keys and an empty `wiki.landing_cards:` placeholder (operator-customizable).
3. **Given** an orchestrator-managed key whose schema has changed between releases, **When** the install-template refresh runs, **Then** the new schema is applied to the orchestrator-managed key and the operator-authored keys remain untouched (schema-evolution behavior for operator-authored keys is #Q-5).
4. **Given** a malformed `.orchestrator/config.yml` (yaml parse failure), **When** the install-template refresh runs, **Then** the refresh aborts with a clear diagnostic naming the parse error and writes nothing (fail-closed, no silent overwrite).

### User Story 6 — Tag-driven nav subgrouping reduces flat-list nav fatigue (Priority: P2)

After US-2 lands, reference nav reads as human strings — but a 70-entry flat list of human strings is still a flat list. The operator wants `wiki-generate-nav.sh` to read `topic_tags:` from each chunk and group entries into deterministic config-driven buckets (e.g., `qso` → "QSO letters", `pbj-policy-manual` → "Policy manuals & FAQs"). Bucket mapping is declared in `.orchestrator/config.yml` under a new `wiki.nav_buckets:` schema. P02 starts with the cheap path (tag-driven grouping in the nav generator + config-driven mapping) and defers `mkdocs-awesome-pages-plugin` adoption unless tag-driven grouping does not generalize cleanly across regulatory-doc / training-material sections. Composes with `navigation.collapse` + `navigation.prune` mkdocs.yml features once subgroups exist.

**Why this priority**: P2 because US-2 (`version:` → nav title) already restores readability per-entry; subgrouping is the next quality lift, but flat human-string lists are usable. Deferring to P02 lets PBJ team's first feedback signal inform the bucket-mapping choices before we lock them.

**Independent Test**: `tests/m037-acceptance/p02-tag-driven-nav-subgrouping.sh` against a fixture chunk corpus with three tag values mapped to three buckets in config: run the nav generator → assert the rendered nav YAML groups entries under their bucket headings, entries with no `topic_tags:` fall under an "Uncategorized" sibling bucket (no exclusion), and the bucket order matches the config declaration order (deterministic).

**Acceptance Scenarios**:

1. **Given** a fixture corpus where each chunk carries a `topic_tags:` value mapped in config, **When** the nav generator runs, **Then** entries appear under their bucket heading and the bucket order matches config declaration order.
2. **Given** a chunk with `topic_tags:` matching no configured bucket, **When** the generator runs, **Then** the chunk renders under an "Uncategorized" sibling bucket (no silent exclusion).
3. **Given** a chunk with multiple `topic_tags:` values, **When** the generator runs, **Then** the chunk renders under the first matching bucket per config declaration order (first-match-wins; multi-bucket cross-listing deferred to a future milestone).
4. **Given** `navigation.collapse` + `navigation.prune` are added to mkdocs.yml alongside subgrouping, **When** the wiki renders, **Then** unselected buckets collapse and the current section's siblings remain visible (no dead-end UX where the reader loses context after clicking).

### User Story 7 — GitHub source-link rewrite for Tier 0 + Tier 1 chunks (Priority: P2)

Reference chunks today carry `external_pointer:` values shaped as `file://<repo-root>/<rel-path>` — useful to the operator running locally, opaque to a remote reader. The operator wants the stub generator's metadata-table emission (Tier 0) and the Tier 1 chunk-rendering pass to transform `file://<repo-root>/<rel-path>` → `<repo_url>/blob/<default-branch>/<rel-path>`. `repo_url` is read from `mkdocs.yml`; default branch is read from `git symbolic-ref refs/remotes/origin/HEAD` with fallback to `main`. Pass-through is preserved when `external_pointer:` does not resolve under the project root (don't mangle external URLs).

Tier 0 chunks: the metadata table is the only pointer to source, so the rewrite is the difference between a usable and unusable chunk for remote readers. Tier 1 chunks: extracted plaintext renders inline, but readers may want the original PDF for layout / figures / signed letterhead — the source link is the affordance.

**Why this priority**: P2 because remote readers (PBJ team, validator pilots) will hit chunk pages whose source affordance currently points at `file://` URLs that only work for the operator. Defer to P02 because the fix is a stub-generator and chunk-projection change scoped enough to wait for first PBJ feedback to confirm the rewrite shape.

**Independent Test**: `tests/m037-acceptance/p02-github-source-link-rewrite.sh` against a fixture chunk with a known `external_pointer:` resolving under the fixture's project root: pre-condition: fixture's `mkdocs.yml` carries `repo_url: https://github.com/example/example`; run the stub generator + Tier 1 projection; assert the rendered chunk metadata table contains `https://github.com/example/example/blob/main/<rel-path>` and the rendered Tier 1 sidebar carries the same link; run a second fixture with a non-resolving `external_pointer:` (URL outside project root); assert the original `external_pointer:` is preserved byte-identical.

**Acceptance Scenarios**:

1. **Given** a Tier 0 chunk with `external_pointer: file:///abs/path/to/<project-root>/<rel-path>`, **When** the stub generator runs, **Then** the rendered metadata table contains `<repo_url>/blob/<default-branch>/<rel-path>` and the original `external_pointer:` value remains in the source chunk frontmatter (rewrite is a projection-time transform, not a source-side mutation).
2. **Given** a Tier 1 chunk, **When** the chunk is rendered, **Then** a sidebar source-link is inserted pointing at the GitHub URL.
3. **Given** an `external_pointer:` value pointing outside the project root (e.g., a vendor URL), **When** the rewrite runs, **Then** the value is preserved byte-identical.
4. **Given** `git symbolic-ref refs/remotes/origin/HEAD` fails (detached or no remote), **When** the rewrite runs, **Then** the default branch falls back to `main` and a debug-level diagnostic is emitted.

### User Story 8 — Knowledge page card grid restructures `/knowledge/` for readability (Priority: P2)

`/knowledge/` today renders the auto-projected `knowledge.md` content — useful as a power-user index, opaque as a landing page. The operator wants `/knowledge/` to become a reader-friendly card grid (reusing the US-1 template) surfacing major knowledge areas as cards (analysis schema, glossary, copy library, source-doc registry, etc.). The auto-projected content remains accessible at a power-user URL (`/knowledge/_index/` or similar — final shape decided after PBJ feedback). ## Edge Cases

- **`wiki.landing_cards:` `section:` value points at a non-existent nav section**: US-1 Acceptance Scenario 3 — render the card with a placeholder href and a build-time diagnostic, do not fail the build. Operator fixes via config edit.
- **Source chunk `version:` field contains markdown-active characters (backticks, brackets)**: US-2 — the stub generator MUST quote the `version:` value in the stub's frontmatter to preserve it byte-identical in the rendered nav YAML. Edge case handled at generator level, not at chunk-source level.
- **Legacy `### DR-CODE-NNN — Title` heading rendered before US-3 lands**: existing `#dr-code-nnn` permalinks were originally derived by mkdocs-material from heading text via auto-anchoring; US-3 preserves the same anchor via `attr_list` `{ #dr-code-nnn }` so inbound links survive (US-3 Acceptance Scenario 1). A pre-merge link-checker run validates this.
- **`mkdocs.yml` already has `navigation.tabs` declared by an operator** (advanced consumer): US-4 — the template-refresh logic detects the existing key and leaves it byte-identical (per US-5 clobber-fix semantics applied to mkdocs.yml as well — exact scope of the merge logic across `config.yml` only vs. all template files is #Q-4).
- **Operator's `repo_url:` in `mkdocs.yml` points at a non-GitHub host** (GitLab / Bitbucket / self-hosted): US-4 / US-7 — the `edit_uri` and source-link rewrites produce `<repo_url>/edit/...` and `<repo_url>/blob/...` paths that may not resolve correctly on non-GitHub hosts. Document as known gap; deferred to a future milestone (multi-host adapter).
- **`config.yml` clobber fix encounters a malformed YAML file**: US-5 Acceptance Scenario 4 — fail-closed with a clear diagnostic, write nothing.
- **`topic_tags:` → `tags:` adapter encounters a chunk with a `tags:` field already set on the source** (PBJ-side authoring chose to use `tags:` directly): US-9 — the adapter MUST detect the source `tags:` and not double-write; if both `topic_tags:` and `tags:` are set with conflicting values, emit a diagnostic and prefer source `tags:` (operator-authored wins).

- **`mkdocs-git-revision-date-localized` invoked on a content page with no git history** (uncommitted): US-9 — the plugin falls back to the file's mtime; no build failure.
- **Card-grid template renders with no cards** (empty `wiki.landing_cards:` and no nav sections, e.g., a freshly initialized wiki with no content yet): US-1 — the homepage falls back to the legacy `index.md` content (current behavior); a card grid with zero cards is not emitted.

- **`gh` is unavailable / unauthenticated during `wiki-init`**: US-11 + US-12 — F12's `gh api -X PUT ... build_type=workflow` and F13's visibility-detection both gracefully degrade. F12 prints a manual fallback with the exact command; F13 falls back to `public` site_url shape (non-destructive default — operators on private repos manually flip `site_url: ""` if they hit the unstyled-404 symptom). Both emit a single diagnostic naming the missing capability so the operator knows what to remediate.
- **Workflow file already exists at `.github/workflows/pages.yml`** (operator hand-authored or pre-existing for unrelated purposes): US-11 — the install template detects the file and follows CON-3 preservation semantics (do not clobber); a diagnostic notes the existing workflow and points the operator at the verbatim reference YAML so they can reconcile manually if desired.

Documentation-side concern only; F13's empty-`site_url` strategy is rotation-agnostic (relative paths work at any URL).

## Constitution Check

- **Principle I (Context Minimization)**: M037 reduces reader-side context cost. - **Principle V (Fresh Context Per Unit)**: each user story carries an Independent Test that exercises that story against a synthetic fixture without dependence on neighboring stories. P01's five stories are independently shippable on top of the minimal slice (US-1+US-2+US-4); P02's four stories are independently shippable on top of P01.

The projection rebuilds from source on every run. Operator-authored content (US-5 `config.yml` clobber fix, US-3 DECISIONS.md heading-shape migration) lives on disk and is the authority — the framework reads, never overwrites.
- **Principle VII (Knowledge Compounds)**: the FR-7 / FR-8 DR-### authoring convention is a knowledge-compounding move — once promoted, every future decision entry follows the convention and the readability benefit cascades through every cross-reference path.
