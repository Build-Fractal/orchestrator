## Notes

### Acceptance script naming preservation (MIT-002)

The three SC-4/5/6 acceptance scripts are named `p04-materials-intake.sh`, `p04-ideation.sh`, and `p05-migrate-routing.sh` — note that the migrate-routing script carries a `p05-` prefix even though the work happens in P04. This is intentional and load-bearing per the spec's MIT-002 amendment to SC-14: P05's `run-acceptance-battery.sh` enumerates the 13 named acceptance scripts by **explicit filename**, NOT by phase prefix. The naming is the spec contract; renaming to `p04-migrate-routing.sh` would break the battery's discovery model.

### Spec-shape vs implementation-shape `--from` flag mapping (FR-11)

The spec's FR-11 contract names the operator-facing flag as `--from gsd-v1|gsd-v2|spec-kit`. The underlying `scripts/migrate/migrate.sh` (closed M015) accepts `--source gsd1|gsd2|speckit`. The migrate-routing layer in `start.sh` is responsible for the translation: the **printed proposed command line** uses the spec-shape (`orchestrator:migrate --from gsd-v1`) per the operator-facing contract, and the **invocation** uses the implementation-shape (`bash scripts/migrate/migrate.sh --path <project-dir> --source gsd1`). Both forms must appear in start.sh as load-bearing tokens for the SC-6 acceptance script to verify both halves.

### MIT-007 `[<context-file>]` wiring is non-skippable in ideation

Per FR-10's MIT-007 amendment, ideation.sh MUST pass the accumulator `partial-answers.yml` as the third argument on EVERY `ask_one` invocation, not only on resume-from-interruption invocations. P02's grilling-shell already gates contradiction detection on the presence of the `[<context-file>]` arg (`if [ -n "$context_file" ]; then _grilling_check_contradiction ...`), so the load-bearing surface in ideation.sh is the unconditional third-arg pass. The SC-5 contradiction-detection assertion exercises this directly via a scripted-contradiction answers file.

### `mktemp -d` staging for byte-deterministic intake outputs (SC-4)

The SC-4 byte-deterministic invariant — same fixture + same answers → byte-identical reconciled-pre-spec — is verified by running materials-intake.sh against two parallel `mktemp -d` staging copies of the PBJ fixture. The intake driver MUST honor an `M033_INTAKE_TIMESTAMP` env override that pins the `<timestamp>` directory name; without this, parallel runs would produce different `<timestamp>` directory paths and the body content would still match but the test harness needs a single canonical path to `diff` against. This env override is a test-only escape valve — production invocations do not set it and get the natural ISO 8601 `date -u` timestamp.

### FR-12 dup-prevention happens inside ingest-codebase, not in start.sh

The duplicate-MEM prevention contract per US-6 AS-3 / brief #Q-10 is enforced inside `scripts/lifecycle/ingest-codebase.sh`'s emit functions: each emit function checks for an existing on-disk MEM at the candidate stable-ID path with `derived_from_migrate: true` frontmatter; on match, the emit is skipped with `skip-duplicate-from-migrate: <stable-id>` to stdout. start.sh's role is simply to invoke `ingest-codebase.sh --project-dir <fixture>` after migrate.sh succeeds (when `src/` is present). The migrate.sh internals (M015 closed) are not modified — the dup-prevention sentinel is a one-way write contract from migrate.sh's emitted MEMs to ingest-codebase.sh's check.

### P01 stub-rewiring is behavior-preserving, not behavior-replacing

T01/T02/T04 each replace one of P01's vacuous sub-flow stubs (`materials_intake_stub`, `ideation_stub`, `migrate_routing_stub`) with the real implementation. The scope-guard verifier asserts the change is behavior-preserving: P01's SC-1 acceptance script (`tests/m033-acceptance/p01-start-branch-routing.sh`) still exits 0 against the post-P04 tree. The P01 stubs printed `would-execute: <stub-name>` tokens; the post-P04 real implementations print different tokens (`materials-intake-completed:`, `ideation-completed:`, `migrate-routed: from=...`). SC-1 was authored against the would-execute tokens — the cross-phase regression verifier validates that SC-1's assertions are token-shape-tolerant (they match either form) OR that SC-1 has been updated in lockstep. T04 specifically MUST verify SC-1 still passes; if SC-1's assertions hard-coded `would-execute: migrate-routing-stub` as a literal, T04 must update SC-1 to accept the new `migrate-routed: from=` token instead. This is the AD-15 cross-phase regression discipline made concrete.
